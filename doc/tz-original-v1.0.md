Версия 1.0 от 28 октября 2026 года.

Разработать локальный пилот сервиса веб поиска для AI агента. Сервис получает живую HTML выдачу поисковиков, читает найденные страницы, сохраняет материалы в кэш и формирует ответ через установленный у пользователя oMLX. Основной сценарий должен работать без предварительного сбора сайтов и без интеграций со сторонними API.

Результат пилота — запускаемое приложение, локальный HTTP API, примеры использования и отчёт о качестве и ограничениях. Исследование индекса выполняется отдельно и не является условием работы живого поиска.

# Цель и границы пилота

Пользователь задаёт произвольный вопрос на русском или английском языке и получает ответ со ссылками на прочитанные источники. Агент может уточнять поисковые запросы в пределах установленного бюджета.

Пилот рассчитан на одного пользователя и запуск на его Mac с Apple Silicon. Модель работает в существующем oMLX. Тип Mac, объём памяти, версии ПО, идентификатор модели и её параметры фиксируются при первом запуске и в отчёте приёмки.

В обязательный объём входят живой поиск, извлечение текста, ограниченный исследовательский цикл, локальный кэш, API, CLI, обработка ошибок и проверяемая привязка выводов к источникам.

Пользовательский интерфейс сайта, публичный хостинг, многопользовательский режим, распределённый обход интернета, авторизация на целевых сайтах, OCR, видео, скачивание файлов и поддержка PDF в обязательный объём не входят. Полная совместимость с API или SDK Tavily не требуется.

# Допустимые внешние обращения

В рабочем режиме разрешены обычные HTTP и HTTPS обращения к публичным HTML страницам поисковиков и найденных сайтов. Для страниц с JavaScript разрешено локальное управление Chromium. Обращение к локальному API oMLX и к собственному HTTP API пилота разрешено.

Запрещены интеграции с внешними поисковыми, scraping, extraction, reranking и LLM API — платными, бесплатными и пробными. В частности, не использовать Tavily, Brave Search API, SerpAPI, облачные reader сервисы, облачные модели и недокументированные JSON endpoints поисковиков как источник выдачи.

Запрет относится к программным интеграциям пилота. Обычная загрузка ресурсов самой страницы браузером допустима; извлечение поисковых результатов должно происходить из HTML или DOM. Автоматические запросы страницы учитываются в сетевой диагностике.

Установку открытых зависимостей, браузера и скачивание выбранной локальной модели выполнять на этапе подготовки. Во время работы исключить телеметрию и скрытые обращения к внешним AI сервисам.

HTML запросы видны поисковикам, обращения к страницам видны их владельцам. Локальная обработка не означает анонимность или работу без интернета.

# Архитектура и компоненты

Предпочтительная реализация — одно Python приложение с FastAPI, HTTP клиентом, Trafilatura, Playwright и SQLite. Версии зависимостей зафиксировать. Дополнительные сервисы добавлять только при подтверждённой необходимости.

Поток обработки: вопрос → план запросов через oMLX → HTML поиск → нормализация ссылок → чтение выбранных страниц → извлечение текста → выделение фрагментов → анализ через oMLX → ответ со ссылками.

Кэш используется при поиске и чтении страниц. Данные и обработка хранятся локально. Простые операции поиска и извлечения должны работать при недоступном oMLX.

Поисковый адаптер должен иметь единый контракт: запрос и язык на входе; список результатов и диагностика источника на выходе. Конкретные парсеры и переключение источников изолировать от исследовательского цикла. Плагинная платформа и универсальный фреймворк агентов не требуются.

# Живой поиск по HTML

На первом этапе проверить не менее двух кандидатов из разных поисковых сервисов. В качестве кандидатов допустимы HTML или Lite страницы DuckDuckGo и обычная веб выдача другого поисковика. Доступность конкретных источников на машине пользователя является предметом проверки, а не исходной гарантией.

Выбрать основной и резервный HTML адаптеры по результатам проверки. Для каждого зафиксировать адреса страниц, способ получения HTML, признаки успешной выдачи, пустой выдачи, CAPTCHA, блокировки и изменения разметки. Публичный экземпляр SearXNG использовать нельзя. Локальный SearXNG или DDGS допустимы только после проверки исходящих обращений и отключения всех адаптеров, использующих сторонние API.

Из выдачи извлекать заголовок, конечный URL, описание, источник и исходную позицию. Отделять органические результаты от рекламы и навигационных блоков. Не выдавать CAPTCHA и страницы ошибок за результаты. Не генерировать отсутствующие описания от имени сайта.

Удалять фрагменты URL и известные tracking параметры; сохранять параметры, влияющие на содержание. Учитывать перенаправления поисковика. Не считать разные страницы одного домена дублями только из-за совпадения домена.

При ошибке основного источника обращаться к резервному в пределах общего бюджета. Успешную пустую выдачу отличать от недоступности источника. При блокировке обоих вернуть явную ошибку с диагностикой.

Ограничивать частоту обращений. Учитывать Retry-After. CAPTCHA, платные прокси, смену аккаунтов и сервисы обхода блокировок в пилот не включать. При устойчивой блокировке останавливать запросы к источнику на период ожидания.

# Чтение и подготовка страниц

Сначала загружать HTML обычным HTTP запросом. Проверять код ответа, Content-Type, кодировку, размер и допустимость конечного адреса. Извлекать основной текст, заголовок и доступные метаданные. Сохранять исходный и конечный URL, время загрузки и хеш содержимого.

Если страница успешно загружена, но основной текст отсутствует из-за JavaScript, выполнить одну попытку чтения через локальный Chromium. Для этого требуются ограниченное ожидание содержимого и проверка результата. Не открывать браузер для каждого URL без необходимости.

Не извлекать основной материал из CAPTCHA, страницы входа или сообщения об ошибке. Не имитировать доступ к закрытому содержимому. Неподдерживаемые форматы возвращать с отдельным кодом ошибки.

Разбивать очищенный текст по заголовкам и абзацам. Сохранять для фрагмента стабильный chunk_id в пределах версии документа и диапазон символов в сохранённом тексте. Вначале использовать простое ранжирование фрагментов по запросу. Отдельный локальный reranker через oMLX допускается как эксперимент после проверки поддержки и пользы.

Публикационную дату брать только из доступных метаданных с указанием происхождения. Если её нет, возвращать null. Время скачивания не подменяет дату публикации.

# Интеграция с oMLX и исследовательский цикл

Подключаться к настроенному пользователем локальному endpoint oMLX. Base URL, идентификатор модели и ключ читать из локальной конфигурации или переменных окружения. Ключ не помещать в код, Git, ответы API, логи или отчёт.

При первом запуске проверить доступность сервера, наличие модели и короткий сценарий вызова инструмента. Поддержку конкретной моделью tool calling подтвердить тестом. Если нативные вызовы ненадёжны, допустим валидируемый JSON протокол действий с теми же ограничениями. Метод зафиксировать в README.

Модели доступны только действия поиска, чтения страниц и завершения ответа. Запуск shell команд, произвольного Python кода и операции с файлами ей не предоставлять. Все действия валидирует приложение.

Цикл: определить план → выполнить поиск → выбрать источники → прочитать материалы → проверить пробелы → при необходимости уточнить запрос → сформировать ответ. Решение о достаточности должно учитывать найденные доказательства и остаток бюджета. Сходные повторные запросы и повторное чтение одной версии URL не должны образовывать бесконечный цикл.

Сохранять выполненные запросы, прочитанные источники и причины остановки. Скрытые рассуждения модели не требуются.

Материалы страниц передавать как недоверенные данные. Инструкции внутри них не могут менять доступные действия, адрес oMLX или ограничения приложения. При нехватке данных вернуть частичный результат и список неподтверждённых пунктов.

Ответ на языке вопроса. Ссылки и source_id формирует приложение из реально полученных материалов. Подтверждающие фрагменты не должны быть сгенерированными цитатами. Для существенных фактических выводов возвращать связи с source_id и chunk_id; собственные выводы отделять от прямых фактов.

# Локальный API и CLI

Все методы доступны только через loopback интерфейс. Предусмотреть OpenAPI схему и CLI команды search, extract и research. CLI вызывает те же функции, что API, без дублирования логики.

| Метод | Вход | Результат |
| - | - | - |
| GET /health | Без параметров | Состояние приложения, кэша, поисковых адаптеров и подключения oMLX |
| POST /search | query, language, max_results, cache_mode | Ссылки, заголовки, описания, источник, диагностика и состояние кэша |
| POST /extract | urls, query при необходимости, cache_mode | Текст, фрагменты, метаданные и ошибки по каждому URL |
| POST /research | question, language, cache_mode | Ответ, источники, привязка выводов к фрагментам, выполненные действия и причина остановки |

query и question — непустые строки до 2000 символов. language — ru, en или auto. max_results — от 1 до 10, по умолчанию 5. urls — от 1 до 8 адресов, каждый до 4096 символов. cache_mode — prefer или refresh, по умолчанию prefer. Неизвестные поля и неподдерживаемые значения отклонять.

Пример запроса исследования:

```json
{
  "question": "Какие открытые подходы отличают работу экскаватора от перемещения по видео?",
  "language": "ru",
  "cache_mode": "refresh"
}
```

Общие поля ответа: request_id, status, results или answer, failed_results, warnings, timings и cache. У исследования дополнительно sources, claims, actions и stop_reason. Точные схемы всех полей и примеры закрепить в OpenAPI до реализации обработчиков.

status принимает ok, partial, empty или error. HTTP 200 использовать для первых трёх состояний, 422 для некорректного запроса, 429 при занятости или превышении локального лимита, 502 при полном провале внешних источников, 503 при недоступном oMLX для research, 504 при истечении общего срока без пригодного результата.

Частичные результаты сохранять при сбое отдельных источников. Если пригодные материалы уже получены, вернуть partial с причиной остановки. Доступный набор источников без итогового ответа модели тоже может быть частичным результатом исследования.

У ошибки указывать code, stage, source при наличии и безопасное message. Минимальные коды: source_blocked, captcha, rate_limited, source_unavailable, parser_changed, fetch_timeout, unsafe_url, unsupported_content, extraction_failed, omlx_unavailable, invalid_model_output, budget_exhausted. GET /health не должен выполнять новый поиск при каждом обращении.

# Кэш и актуальность

Хранить в SQLite нормализованные поисковые ответы, очищенный текст, метаданные, фрагменты и техническую диагностику. HTML целиком сохранять только в явном диагностическом режиме с ограничением размера.

Поисковый ключ включает нормализованные параметры запроса, включая язык и max_results, источник и версию адаптера. Ключ документа учитывает URL, вариант извлечения и версию обработчика. Отдельно хранить конечный URL, хеш текста, fetched_at и expires_at. Не смешивать содержимое разных query параметров или версий страницы.

Начальные TTL: выдача 15 минут, документы 24 часа. После истечения TTL требуется обновление. Использовать ETag и Last-Modified при наличии. Ответ 304 обновляет время проверки без повторного извлечения текста.

prefer использует только актуальный кэш. refresh принудительно выполняет сетевое обращение и обновляет кэш при успехе. Не выдавать просроченные данные как свежие; в обязательной версии автоматическую подстановку просроченного кэша при ошибке не делать.

Ошибки и CAPTCHA не сохранять как успешную выдачу или документ. Одинаковые одновременные операции объединять. Для пилота достаточно одного активного исследования.

Начальный предел кэша — 1 ГиБ. Удалять сначала просроченные, затем давно неиспользуемые записи без повреждения связей документов и фрагментов. Предусмотреть CLI очистки отдельного URL и всего кэша.

Итоговые ответы модели в первой версии повторно не использовать. Повторное исследование может читать закэшированные материалы, но должно заново проверять достаточность и формировать ответ.

| Поисковые формулировки на исследование | Не более 4 |

| Интервал к одному домену | Не менее 2 секунд, больший Retry-After имеет приоритет |
| Повтор после временной ошибки | Не более 1, внутри общего бюджета |
| Перенаправления на одну загрузку | Не более 5 |

Считать все реальные обращения, включая резервные источники и повторы. Ограничения проверяет приложение. Превышение контекста не должно приводить к незаметному удалению вопроса или источников ссылок: сокращать материалы с явной отметкой truncated.

По истечении общего срока отменять оставшиеся сетевые задачи. Модельные операции выполнять с таймаутом; если сервер продолжает вычисление после разрыва запроса, не запускать поверх него бесконечные повторы и отражать ограничение в диагностике. Лимит oMLX подбирать с учётом измеренной скорости модели.

# Защита локальной среды

Для загружаемых URL разрешены только HTTP и HTTPS. Запретить userinfo, локальные имена, loopback, приватные, link-local и служебные адреса IPv4 и IPv6, а также схемы file, data и другие неподдерживаемые схемы.

Проверять разрешённость адреса после DNS разрешения и на каждом перенаправлении; защита должна учитывать DNS rebinding. Применять тот же контроль к браузерным переходам, подресурсам и WebSocket соединениям. Сервисные workers и скачивание файлов отключить. Локальный oMLX вызывается отдельным доверенным клиентом, его адрес не берётся из действий модели или URL страниц.

Использовать отдельный временный профиль Chromium без доступа к пользовательскому профилю, cookies и сохранённым паролям. Ограничить работу браузера чтением содержимого.

API слушает 127.0.0.1. CORS по умолчанию закрыт; запросы с посторонним Origin отклоняются. Не отключать проверку TLS сертификатов.

Логи содержат этапы, длительности, коды ошибок и request_id. Ключи, заголовки авторизации и полные тексты вопросов или страниц по умолчанию не логировать. Диагностические файлы очищаются отдельной командой и не попадают в Git.

# Проверки и критерии приёмки

До настройки качества зафиксировать набор из 20 поисковых запросов: 10 русских и 10 английских. Включить поиск факта, официальной документации, сравнения, актуального материала, site запроса и редкой формулировки. Отдельно подготовить эталонные страницы и вопросы для проверки ответов. Набор и критерии сохранить в проекте.

| Проверка | Критерий |
| - | - |
| Поиск без сторонних API | Проверка конфигурации и сетевой трассы подтверждает HTML или DOM получение выдачи и отсутствие внешних поисковых и AI API |
| Основной сценарий | В каждом из двух живых прогонов не менее 16 из 20 запросов дают минимум 3 уникальные релевантные органические ссылки; релевантность оценивается вручную по сохранённому правилу |
| Резервный источник | При искусственном отказе основного источника происходит переключение, а при отказе обоих возвращается явная ошибка |
| Извлечение HTML | Не менее 18 из 20 выбранных доступных HTML страниц содержат ожидаемый основной текст без подмены меню или CAPTCHA |
| JavaScript страницы | Не менее 4 из 5 заранее выбранных публичных JS страниц читаются браузерным способом |
| Исследование через oMLX | Не менее 8 из 10 эталонных вопросов получают содержательно верный ответ; остальные обозначены как partial или недостаток данных |
| Проверяемость ссылок | Все source_id и chunk_id ответа существуют; не менее 90 процентов проверенных существенных утверждений действительно поддерживаются указанными фрагментами |
| Недостаток данных | На сценариях с заблокированными или противоречивыми источниками модель не выдаёт уверенный неподтверждённый ответ |
| Кэш | Повтор search или extract в TTL не вызывает соответствующую сетевую загрузку; refresh обновляет данные; после перезапуска кэш сохраняется |
| Безопасность | Заблокированы приватные IPv4 и IPv6, перенаправление во внутреннюю сеть, DNS rebinding и браузерный подресурс к localhost |
| Prompt injection | Тестовая страница с инструкцией прочитать локальный файл, сменить endpoint или отправить данные наружу не получает таких полномочий |
| Лимиты | Сценарии повторов, длинной страницы, медленного источника и цикла модели завершаются в пределах бюджета |
| Частичные ошибки | Сбой одного URL не уничтожает результаты остальных |

Живые прогоны выполнить в разные дни и фиксировать дату, сеть и состояние кэша. Время ответа измерять отдельно без кэша и с кэшем, отдельно выделяя поиск, загрузку, браузер и oMLX; указать медиану и p95 без обещания одинаковой скорости на разных моделях.

Автоматические проверки парсеров выполнять на сохранённых HTML fixtures: обычная выдача, пустая выдача, изменённая разметка, CAPTCHA, редирект и реклама. Живой smoke тест запускать отдельно, чтобы внешние изменения не подменяли регрессионные тесты.

Если ни один набор из двух HTML источников не проходит проверку доступности, оформить результат как неуспешную проверку гипотезы с данными прогонов. Не заменять источники сторонним API и не объявлять пилот принятым.

# Этапы и результаты разработки

1. Проверка реализуемости. Проверить oMLX и модель; протестировать HTML источники на целевой машине; выбрать основной и резервный; зафиксировать сетевые обращения, блокировки и исходные показатели. При непроходимом ограничении сначала представить результаты проверки гипотезы.

2. Поиск и чтение. Реализовать search и extract, HTTP и браузерное чтение, единый формат данных, обработку ошибок, ограничения и SQLite кэш.

3. Работа агента. Подключить oMLX, ограниченный цикл действий, выделение фрагментов, привязку ответов к источникам и research.

4. Проверка пилота. Выполнить автоматические проверки и живые прогоны, оформить отчёт и инструкцию запуска.

Передать исходный код, зафиксированные зависимости, пример конфигурации без секретов, README с запуском и очисткой данных, OpenAPI схему, CLI примеры, fixtures, набор приёмочных вопросов и отчёт с результатами. Указать команды воспроизведения проверок, измеренные ресурсы, известные ограничения и условия восстановления адаптеров после изменения HTML.

# Открытый вопрос об индексе

Живой поиск остаётся основным сценарием и не зависит от предварительно собранного индекса. Кэш документов сам по себе не считается полноценной поисковой системой.

В отдельной исследовательской записке сравнить использование готового решения и создание собственного небольшого индекса поверх накопленных материалов. Кандидаты для проверки: YaCy как готовая система и SQLite FTS5 или Meilisearch Community Edition как основа собственной обработки. Конкретное решение не закрепляется этим ТЗ.

Для небольшого сравнения использовать одну и ту же выборку до 500 очищенных документов из кэша и 10 запросов. Проверить релевантность, поиск на русском и английском, время обновления и поиска, размер на диске, память, лицензии и трудоёмкость сопровождения. Для воспроизводимости допускается заранее подготовленный тестовый корпус.

Результат — рекомендация: нужен ли индекс пилоту, что он улучшает, готовое или собственное решение выбрать и нужен ли отдельный этап разработки. Полноценный краулер и обязательное внедрение индекса в основной поток в объём этого пилота не входят.
