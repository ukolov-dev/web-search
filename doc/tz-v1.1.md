# Техническое задание на пилот живого веб-поиска с локальным oMLX

**Версия 1.1 от 28 октября 2026 года.**

Редакция заменяет v1.0 для дальнейшей разработки. В неё включены рекомендации литературного обзора: контракт доказательств, условия остановки, диагностика ошибок, оценка полноты и безопасности. [Исходная v1.0](tz-original-v1.0.md) сохранена для сравнения. Научные основания приведены в конце документа; конкретные схемы, численные пределы и пороги приёмки являются требованиями этого пилота, а не гарантированными результатами публикаций.

Разработать локальный пилот сервиса веб поиска для AI агента. Сервис получает живую HTML выдачу поисковиков, читает найденные страницы, сохраняет материалы в кэш и формирует ответ через установленный у пользователя oMLX. Основной сценарий должен работать без предварительного сбора сайтов и без интеграций со сторонними API.

Результат пилота — запускаемое приложение, локальный HTTP API, примеры использования и отчёт о качестве и ограничениях. Исследование индекса выполняется отдельно и не является условием работы живого поиска.

# Цель и границы пилота

Пользователь задаёт произвольный вопрос на русском или английском языке и получает ответ со ссылками на прочитанные источники. Агент может уточнять поисковые запросы в пределах установленного бюджета.

Пилот рассчитан на одного пользователя и запуск на его Mac с Apple Silicon. Модель работает в существующем oMLX. Тип Mac, объём памяти, версии ПО, идентификатор модели и её параметры фиксируются при первом запуске и в отчёте приёмки.

В обязательный объём входят живой поиск, извлечение текста, ограниченный исследовательский цикл, локальный кэш, API, CLI, обработка ошибок, проверяемая привязка утверждений к версиям источников и воспроизводимый отчёт о качестве.

Базовая версия использует простое ранжирование исходных фрагментов. Обучение или дообучение моделей, RL, многомодельное обсуждение, отдельный классификатор сложности, генеративное сжатие и отдельный reranker не являются обязательными. Последние два подхода допускаются как локальные эксперименты после измерения базовой версии; их вызовы и ресурсы учитываются в общем бюджете. Дополнительные сервисы и полноценный поисковый индекс не должны становиться условием запуска основного сценария.

Пользовательский интерфейс сайта, публичный хостинг, многопользовательский режим, распределённый обход интернета, авторизация на целевых сайтах, OCR, видео, скачивание файлов и поддержка PDF в обязательный объём не входят. Полная совместимость с API или SDK Tavily не требуется.

# Допустимые внешние обращения

В рабочем режиме разрешены обычные HTTP и HTTPS обращения к публичным HTML страницам поисковиков и найденных сайтов. Для страниц с JavaScript разрешено локальное управление Chromium. Обращение к локальному API oMLX и к собственному HTTP API пилота разрешено.

Запрещены интеграции с внешними поисковыми, scraping, extraction, reranking и LLM API — платными, бесплатными и пробными. В частности, не использовать Tavily, Brave Search API, SerpAPI, облачные reader сервисы, облачные модели и недокументированные JSON endpoints поисковиков как источник выдачи.

Запрет относится к программным интеграциям пилота. Обычная загрузка ресурсов самой страницы браузером допустима; извлечение поисковых результатов должно происходить из HTML или DOM. Автоматические запросы страницы учитываются в сетевой диагностике.

Установку открытых зависимостей, браузера и скачивание выбранной локальной модели выполнять на этапе подготовки. Во время работы исключить телеметрию и скрытые обращения к внешним AI сервисам.

HTML запросы видны поисковикам, обращения к страницам видны их владельцам. Локальная обработка не означает анонимность или работу без интернета.

# Архитектура и компоненты

Предпочтительная реализация — одно Python приложение с FastAPI, HTTP клиентом, Trafilatura, Playwright и SQLite. Версии зависимостей зафиксировать. Дополнительные сервисы добавлять только при подтверждённой необходимости.

Поток обработки: вопрос → план запросов через oMLX → HTML поиск → нормализация ссылок → чтение выбранных страниц → извлечение текста → выделение фрагментов → анализ через oMLX → ответ со ссылками.

Кэш используется при поиске и чтении страниц. Данные и обработка хранятся локально. Простые операции поиска и извлечения должны работать при недоступном oMLX.

Поисковый адаптер должен иметь единый контракт: запрос и язык на входе; список результатов и диагностика источника на выходе. Конкретные парсеры и переключение источников изолировать от исследовательского цикла. Плагинная платформа и универсальный фреймворк агентов не требуются.

# Живой поиск по HTML

На первом этапе проверить не менее двух кандидатов из разных поисковых сервисов. В качестве кандидатов допустимы HTML или Lite страницы DuckDuckGo и обычная веб выдача другого поисковика. Доступность конкретных источников на машине пользователя является предметом проверки, а не исходной гарантией.

Выбрать основной и резервный HTML адаптеры по результатам проверки. Для каждого зафиксировать адреса страниц, способ получения HTML, признаки успешной выдачи, пустой выдачи, CAPTCHA, блокировки и изменения разметки. Публичный экземпляр SearXNG использовать нельзя. Локальный SearXNG или DDGS допустимы только после проверки исходящих обращений и отключения всех адаптеров, использующих сторонние API.

Из выдачи извлекать заголовок, конечный URL, описание, источник и исходную позицию. Отделять органические результаты от рекламы и навигационных блоков. Не выдавать CAPTCHA и страницы ошибок за результаты. Не генерировать отсутствующие описания от имени сайта.

Удалять фрагменты URL и известные tracking параметры; сохранять параметры, влияющие на содержание. Учитывать перенаправления поисковика. Не считать разные страницы одного домена дублями только из-за совпадения домена.

При ошибке основного источника обращаться к резервному в пределах общего бюджета. Успешную пустую выдачу отличать от недоступности источника. При блокировке обоих вернуть явную ошибку с диагностикой.

Ограничивать частоту обращений. Учитывать Retry-After. CAPTCHA, платные прокси, смену аккаунтов и сервисы обхода блокировок в пилот не включать. При устойчивой блокировке останавливать запросы к источнику на период ожидания.

# Чтение и подготовка страниц

Сначала загружать HTML обычным HTTP запросом. Проверять код ответа, Content-Type, кодировку, размер и допустимость конечного адреса. Извлекать основной текст, заголовок и доступные метаданные. Сохранять исходный и конечный URL, время загрузки и хеш содержимого.

Если страница успешно загружена, но основной текст отсутствует из-за JavaScript, выполнить одну попытку чтения через локальный Chromium. Для этого требуются ограниченное ожидание содержимого и проверка результата. Не открывать браузер для каждого URL без необходимости.

Не извлекать основной материал из CAPTCHA, страницы входа или сообщения об ошибке. Не имитировать доступ к закрытому содержимому. Неподдерживаемые форматы возвращать с отдельным кодом ошибки.

Разбивать очищенный текст по заголовкам и абзацам. Для каждой сохранённой версии очищенного текста назначать document_version и вычислять text_hash. Идентичность версии учитывает сам текст, вариант извлечения и версию обработчика. Изменение текста или правил его обработки не должно переназначать старые идентификаторы новому содержимому.

Сохранять для фрагмента стабильный chunk_id в пределах document_version и диапазон [start, end) в Unicode code points сохранённой строки. Диапазоны вычисляются после всех преобразований текста; повторная нормализация строки после вычисления диапазонов не допускается. Проверять 0 ≤ start < end ≤ длина текста. Правило применяется одинаково к кириллице, латинице и emoji.

Вначале использовать простое ранжирование фрагментов по запросу. Сохранять перечень и порядок фрагментов, фактически переданных модели. Повторяющийся текст не должен вытеснять все остальные релевантные источники. Генеративная выжимка при экспериментальном сжатии не заменяет оригинальное доказательство и должна сохранять связь с ним.

Публикационную дату брать только из доступных метаданных с указанием происхождения. Если её нет, возвращать null. Время скачивания не подменяет дату публикации.

# Интеграция с oMLX и исследовательский цикл

Подключаться к настроенному пользователем локальному endpoint oMLX. Base URL, идентификатор модели и ключ читать из локальной конфигурации или переменных окружения. Ключ не помещать в код, Git, ответы API, логи или отчёт.

При первом запуске проверить доступность сервера, наличие модели и короткий сценарий вызова инструмента. Поддержку конкретной моделью tool calling подтвердить тестом. Если нативные вызовы ненадёжны, допустим валидируемый JSON протокол действий с теми же ограничениями. Метод зафиксировать в README.

Модели доступны только действия поиска, чтения страниц и завершения ответа. Запуск shell команд, произвольного Python кода и операции с файлами ей не предоставлять. Все действия валидирует приложение.

Цикл: определить план → выполнить поиск → выбрать источники → прочитать материалы → проверить пробелы → при необходимости уточнить запрос → сформировать ответ. Простой вопрос может завершиться после одного прохода. Ответ исследования должен опираться на прочитанные материалы и при раннем завершении; ответы только из памяти модели не удовлетворяют этому требованию.

Хранить краткий список незакрытых существенных пунктов вопроса. Каждое уточнение поиска связывать с конкретным пробелом, а не с общей просьбой «искать ещё». Решение о достаточности учитывать по покрытию вопроса доказательствами, наличию противоречий и остатку бюджета; самооценка уверенности модели достаточным основанием не является.

Перед выбором следующего действия передавать модели остаток поисковых формулировок, обращений к выдаче, читаемых URL, браузерных попыток, генераций и времени. Ограничения и допуск действия проверяет приложение независимо от вывода модели. Сходные повторные запросы и повторное чтение одной версии URL не должны образовывать бесконечный цикл. Обнаружение отсутствия новых доказательств позволяет завершить исследование раньше предельного бюджета.

Возвращать выполненные действия, прочитанные источники, открытые пункты и причину остановки. Для действия достаточно типа, параметров, идентификаторов полученных результатов, длительности, остатка ресурсов и короткого указания закрываемого пробела. Скрытые рассуждения модели не требуются. Полные параметры доступны вызывающему локальный API; в обычные технические логи они не копируются.

stop_reason принимает одно из значений:

| Значение | Смысл |
| - | - |
| evidence_sufficient | Существенные пункты вопроса покрыты прочитанными доказательствами, значимые противоречия разрешены |
| no_new_evidence | Доступные действия не добавляют пригодных доказательств, включая успешный поиск без результатов |
| sources_unavailable | Дальнейшее получение материалов невозможно из-за отказа или блокировки источников |
| budget_exhausted | Исчерпан лимит действий или генераций до истечения общего срока |
| deadline | Истёк общий срок исследования |
| model_error | Продолжение невозможно из-за недоступности модели или невосстановимого невалидного вывода |

Причина остановки описывает завершение цикла; status отдельно описывает полноту результата. Например, при no_new_evidence возможны partial с найденными материалами или empty без них. Не присваивать evidence_sufficient ответу с существенными незакрытыми пунктами.

Материалы страниц передавать как недоверенные данные. Инструкции внутри них не могут менять доступные действия, адрес oMLX или ограничения приложения. При нехватке данных и наличии пригодных материалов вернуть частичный результат и список неподтверждённых пунктов. При отсутствии пригодных материалов применять правила empty/error из раздела API.

Ответ на языке вопроса. Ссылки и source_id формирует приложение из реально полученных материалов. Существенные утверждения перечислять в claims как отдельно проверяемые единицы со связью с соответствующим местом в итоговом ответе. Несколько независимых фактов в одном предложении проверять отдельно. Прямые факты обозначать как fact, собственные выводы и вычисления — как inference; для выводов указывать исходные доказательства и краткую проверяемую связь с выводом.

Для каждого утверждения возвращать evidence — связи с source_id, document_version и chunk_id. Дословную цитату формирует приложение срезом сохранённого текста, проверяя границы и совпадение; модель не формирует цитату от имени источника. Проверка существования идентификаторов и совпадения цитаты не заменяет семантическую проверку поддержки утверждения.

Утверждение, которое не удалось подтвердить, не представлять как установленный факт. Его указывать в unresolved_points или как явно условный вывод с описанием ограничения. Невалидные идентификаторы не должны попадать в ответ: допускается ограниченное исправление вывода в общем бюджете, а при неудаче вернуть частичные материалы без невалидного ответа модели.

Свежесть загрузки источника не доказывает актуальность факта. Для меняющихся сведений учитывать доступные даты и первичные источники. При ложной предпосылке вопроса явно указать её и привести доказательства. При противоречии материалов показывать содержание расхождения и фрагменты сторон; если разрешить его не удалось, вернуть partial. Перепечатки не считать независимыми подтверждениями и не выбирать версию только по большинству URL.

# Локальный API и CLI

Все методы доступны только через loopback интерфейс. Предусмотреть OpenAPI схему и CLI команды search, extract и research. CLI вызывает те же функции, что API, без дублирования логики.

| Метод | Вход | Результат |
| - | - | - |
| GET /health | Без параметров | Состояние приложения, кэша, поисковых адаптеров и подключения oMLX |
| POST /search | query, language, max_results, cache_mode | Ссылки, заголовки, описания, источник, диагностика и состояние кэша |
| POST /extract | urls, query при необходимости, cache_mode | Текст, версии документов, фрагменты с диапазонами, метаданные и ошибки по каждому URL |
| POST /research | question, language, cache_mode | Ответ, источники, привязка выводов к фрагментам, выполненные действия и причина остановки |

query и question — непустые строки до 2000 символов; необязательный query в extract подчиняется тем же ограничениям. language — ru, en или auto. max_results — от 1 до 10, по умолчанию 5. urls — от 1 до 8 адресов, каждый до 4096 символов. cache_mode — prefer или refresh, по умолчанию prefer. Неизвестные поля и неподдерживаемые значения отклонять.

Пример запроса исследования:

```json
{
  "question": "Какие открытые подходы отличают работу экскаватора от перемещения по видео?",
  "language": "ru",
  "cache_mode": "refresh"
}
```

Общие поля ответа: request_id, status, results или answer, failed_results, warnings, timings и cache. У исследования дополнительно sources, claims, actions, unresolved_points, context и stop_reason. Точные схемы всех полей, обязательность, допустимые null, единицы измерения и примеры закрепить в OpenAPI до реализации обработчиков. Дополнительные поля запроса для этих возможностей не требуются.

Минимальный контракт доказательств и диагностики:

| Объект | Обязательное содержание |
| - | - |
| Источник в sources | source_id, исходный и конечный URL, заголовок, document_version, text_hash, версия извлекателя, fetched_at, checked_at, published_at либо null, происхождение публикационной даты |
| Фрагмент в extract и цитируемые фрагменты в sources | source_id, document_version, chunk_id, start, end, исходный text; признак truncated при сокращении |
| Элемент claims | claim_id, text, kind: fact или inference, answer_start, answer_end, evidence; для inference — краткое основание вывода |
| Элемент evidence | source_id, document_version, chunk_id; при возврате цитаты — её диапазон внутри сохранённого текста и сформированный приложением текст |
| Привязка к ответу | answer_start и answer_end — диапазон [start, end) в Unicode code points итоговой строки answer, после формирования ссылок приложением; text соответствует этому срезу |
| Элемент actions | Тип действия, валидированные параметры, краткая цель, результат или безопасная ошибка, длительность и остаток бюджета |
| unresolved_points | Список существенных пунктов вопроса, оставшихся без достаточной поддержки или с неразрешёнными противоречиями |
| context | Перечень и порядок переданных фрагментов, truncated, объём символов, доступные счётчики токенов и способ их подсчёта |

Если итоговый текст отсутствует, answer равен null, claims — пустой массив; доступные источники и действия сохраняются. Непустой текст без фактических утверждений, например объяснение недостатка данных, допустим, но сам по себе не засчитывается как содержательно правильный ответ на вопрос, имеющий эталонное решение. Связь с версией текста должна быть однозначной в ответе и в сохранённых артефактах приёмки.

status принимает ok, partial, empty или error. ok означает полный пригодный результат метода; partial — полезные материалы или ответ с существенными пробелами; empty — успешно выполненные операции не дали пригодных материалов; error — пригодный результат не получен из-за сбоя. Для search полнота относится к поисковой выдаче, для extract — к запрошенным URL, для research — к исследованию вопроса.

HTTP 200 использовать для ok, partial и empty; 422 — для некорректного запроса; 429 — при занятости или превышении локального лимита; 502 — при полном провале внешних источников либо невосстановимом невалидном выводе доступной модели без пригодных частичных материалов; 503 — при недоступном oMLX для research без пригодных частичных материалов; 504 — при истечении общего срока без пригодного результата. В последних трёх случаях status равен error. Непредвиденная внутренняя ошибка возвращается как HTTP 500 с безопасной диагностикой.

Сначала проверять наличие пригодного частичного результата: сбой источника, модели или истечение срока не должны уничтожать уже полученное. Если лимит действий исчерпан после успешных операций без пригодных материалов, вернуть empty с budget_exhausted; если все выполненные операции завершились отказом, применять соответствующий код ошибки. При совпадении причин остановки приоритет имеет истечение общего срока, затем препятствующий продолжению сбой, затем исчерпание численного лимита. Примеры этих сочетаний закрепить в OpenAPI.

Частичные результаты сохранять при сбое отдельных источников. Если пригодные материалы уже получены, вернуть partial с причиной остановки. Доступный набор источников без итогового ответа модели тоже может быть частичным результатом исследования.

У ошибки указывать code, stage, source при наличии и безопасное message. Минимальные коды: source_blocked, captcha, rate_limited, source_unavailable, parser_changed, fetch_timeout, unsafe_url, unsupported_content, extraction_failed, omlx_unavailable, invalid_model_output, budget_exhausted. GET /health не должен выполнять новый поиск при каждом обращении.

# Кэш и актуальность

Хранить в SQLite нормализованные поисковые ответы, очищенный текст, метаданные, фрагменты и техническую диагностику. HTML целиком сохранять только в явном диагностическом режиме с ограничением размера.

Поисковый ключ включает нормализованные параметры запроса, включая язык и max_results, источник и версию адаптера. Ключ документа учитывает URL, вариант извлечения и версию обработчика. Отдельно хранить конечный URL, document_version, text_hash, fetched_at, checked_at и expires_at. fetched_at — время получения тела сохранённой версии; checked_at — время последней успешной проверки его актуальности. Не смешивать содержимое разных query параметров или версий страницы.

Начальные TTL: выдача 15 минут, документы 24 часа. После истечения TTL требуется обновление. Использовать ETag и Last-Modified при наличии. Ответ 304 обновляет checked_at и expires_at без повторного извлечения текста, изменения fetched_at и document_version. Повторное получение идентичного очищенного текста тем же обработчиком не требует новой версии. TTL характеризует допустимый возраст локальной проверки, а не истинность и актуальность факта в источнике.

prefer использует только актуальный кэш. refresh принудительно выполняет сетевое обращение и обновляет кэш при успехе. Не выдавать просроченные данные как свежие; в обязательной версии автоматическую подстановку просроченного кэша при ошибке не делать.

Ошибки и CAPTCHA не сохранять как успешную выдачу или документ. Одинаковые одновременные операции объединять. Для пилота достаточно одного активного исследования.

Начальный предел кэша — 1 ГиБ. Удалять сначала просроченные, затем давно неиспользуемые записи без повреждения связей документов и фрагментов. Предусмотреть CLI очистки отдельного URL и всего кэша.

Итоговые ответы модели в первой версии повторно не использовать. Повторное исследование может читать закэшированные материалы, но должно заново проверять достаточность и формировать ответ.

В явном режиме приёмочных испытаний сохранять отдельный локальный пакет прогона: request_id/run_id, вопрос и параметры, выбранные очищенные доказательства с версиями и диапазонами, ответ, claims, действия, порядок контекста, настройки модели без секретов, версии адаптеров и извлекателя, ручную разметку и метрики. Это снимок для проверки отчёта; он не зависит от последующего обновления или очистки обычного кэша.

По умолчанию пакеты испытаний хранятся не более 30 дней и занимают суммарно не более 1 ГиБ, отдельно от рабочего кэша. Пределы должны быть настраиваемыми и указанными в README. При запуске и перед сохранением пакета удалять просроченные пакеты, затем старейшие до соблюдения лимита; не сохранять пакет частично без явной ошибки. Предусмотреть CLI-команды очистки пакета по run_id и всех пакетов, а также просмотр их размера и срока хранения. При удалении доказательств помечать связанный отчёт как невоспроизводимый по локальным материалам. Не удерживать бессрочные версии документов только ради старых ссылок.

Полные HTML по-прежнему сохраняются только в отдельном диагностическом режиме. Пакеты испытаний не попадают в Git. Сохранение полного вопроса и выбранных текстов в них выполняется только при явном запуске испытаний и не включается в обычные логи.

Считать все реальные обращения, включая резервные источники и повторы. Ограничения проверяет приложение. В лимит 6 генераций входят планирование, промежуточный анализ, проверка пробелов, исправление формата и итоговый ответ. Резервировать как минимум один оставшийся вызов и время на финал; не использовать весь бюджет на планирование. Это резерв внутри общего лимита, а не дополнительный вызов сверх него. Если финал не удалось получить или исправить в пределах лимита и срока, вернуть имеющиеся материалы как partial без невалидного текста.

Контекст источников ограничен одновременно 24000 символами и доступным окном выбранной модели за вычетом инструкций, вопроса, истории действий и резерва выходных токенов. Размер выходного резерва и способ подсчёта фиксируются в конфигурации и отчёте. Использовать доступный токенизатор модели; при его отсутствии явно обозначать оценку и применять консервативный запас с обработкой ошибки переполнения контекста. Приблизительный подсчёт не выдавать за точный.

Превышение контекста не должно приводить к незаметному удалению вопроса, инструкций или идентификаторов доказательств. Сокращать низкорелевантные фрагменты с явной отметкой truncated, сохраняя перечень реально переданных материалов. Не запускать отдельные проверки или сжатие за пределами численного и временного бюджетов.

По истечении общего срока отменять оставшиеся сетевые задачи. Модельные операции выполнять с таймаутом; если сервер продолжает вычисление после разрыва запроса, не запускать поверх него бесконечные повторы и отражать ограничение в диагностике. Лимит oMLX подбирать с учётом измеренной скорости модели.

# Защита локальной среды

Для загружаемых URL разрешены только HTTP и HTTPS. Запретить userinfo, локальные имена, loopback, приватные, link-local и служебные адреса IPv4 и IPv6, а также схемы file, data и другие неподдерживаемые схемы.

Проверять разрешённость адреса после DNS разрешения и на каждом перенаправлении; защита должна учитывать DNS rebinding. Применять тот же контроль к браузерным переходам, подресурсам и WebSocket соединениям. Сервисные workers и скачивание файлов отключить. Локальный oMLX вызывается отдельным доверенным клиентом, его адрес не берётся из действий модели или URL страниц.

Использовать отдельный временный профиль Chromium без доступа к пользовательскому профилю, cookies и сохранённым паролям. Ограничить работу браузера чтением содержимого.

API слушает 127.0.0.1. CORS по умолчанию закрыт; запросы с посторонним Origin отклоняются. Не отключать проверку TLS сертификатов.

Логи содержат этапы, длительности, коды ошибок и request_id. Ключи, заголовки авторизации и полные тексты вопросов или страниц по умолчанию не логировать. Диагностические файлы очищаются отдельной командой и не попадают в Git.

Модели не передавать ключи, конфигурацию с секретами, локальные файлы и данные пользовательского браузера. Материалы выдачи, заголовки, описания, метаданные и основной текст имеют одинаковый статус недоверенных данных. Валидировать не только тип действия, но и его аргументы. Разрешённые search и read не должны автоматически становиться каналом отправки данных из источников по инструкции этих источников.

Учитывать, что даже без доступа к файлам инъекция способна исказить ответ, подменить доказательства или попытаться включить текст из контекста в новый запрос либо внешний URL. Технические ограничения полномочий и проверка качества содержания — отдельные проверки. Наличие валидного JSON или запрет shell не являются доказательством общей защищённости от prompt injection. Известные ограничения семантического контроля запросов и исходящего потока явно отражать в отчёте.

# Проверки и критерии приёмки

До настройки качества зафиксировать набор из 20 поисковых запросов: 10 русских и 10 английских. Включить поиск факта, официальной документации, сравнения, актуального материала, site запроса и редкой формулировки. Отдельно подготовить 20 эталонных HTML-страниц, 5 JS-страниц и 10 вопросов research: 5 русских и 5 английских. Наборы, их версии и критерии сохранить в проекте. Для настройки промптов использовать отдельный небольшой набор; изменение приёмочного набора после просмотра результатов оформлять новой версией и повторным прогоном.

В research-набор включить не менее двух вопросов каждой группы: простой факт, составной вопрос с зависимыми фактами, сравнение, меняющееся сведение; для каждой группы должны присутствовать RU и EN. Также включить ложную предпосылку и недостаток либо конфликт данных. Свойства могут пересекаться в одном вопросе. Набор должен позволять получить не менее 8 содержательных эталонных ответов; заведомую нехватку данных оценивать по ожидаемому частичному исходу, не подменяя ею порог правильных ответов.

Для каждого вопроса заранее записать case_id, язык, класс, дату актуальности эталона при необходимости, обязательные существенные факты, допустимые варианты ответа, первичные URL и сохранённые подтверждающие фрагменты. Для каждого обычного вопроса содержательная правильность означает правильное раскрытие всех обязательных пунктов без существенного ложного заключения; корректное опровержение ложной предпосылки является содержательным ответом. Для диагностического случая с недостатком данных зафиксировать допустимые открытые пункты и запрещённые уверенные заключения.

Для поисковой релевантности заранее определить: 0 — не относится к запросу, 1 — полезный фон без ответа, 2 — непосредственно помогает ответить на запрос. В критерии «минимум 3 релевантные ссылки» учитывать органические страницы с оценкой 2. Редиректы и копии одной страницы не увеличивают число уникальных релевантных результатов; совпадение домена само по себе не означает дубликат.

## Оценка утверждений и полноты

Единица оценки — атомарное существенное утверждение. Проверять все такие факты в итоговых ответах приёмочной десятки, включая отсутствующие в claims: пропуск факта в структурированном массиве не должен улучшать метрику. Связь утверждения с источником и его истинность относительно эталона оценивать раздельно: источник может содержать устаревшее или ошибочное утверждение.

| Метрика | Расчёт |
| - | - |
| Поддержка цитируемых утверждений | Полностью поддержанные своими фрагментами факты / все факты, имеющие хотя бы одну ссылку |
| Покрытие доказательствами | Полностью поддержанные своими фрагментами факты / все существенные фактические утверждения ответа |
| Полезность привязок | Связи, вносящие релевантную поддержку утверждения / все связи; учитывать совместно необходимые частичные доказательства |
| Полнота ответа | Правильно раскрытые обязательные факты эталона / все обязательные факты эталона |
| Ошибочная уверенность | Сценарии недостатка или противоречия данных с уверенным неподтверждённым ответом / все такие сценарии |

Для выводов и вычислений проверять наличие исходных доказательств и корректность перехода к выводу; не требовать дословного присутствия собственного вывода на странице. Неподтверждённые фактические предпосылки вывода включаются в оценку фактов. Не вводить общий порог для полезности привязок или позиционной устойчивости до измерения базовой версии.

Показывать числители, знаменатели, оценки каждого вопроса, общие показатели и раздельные RU/EN. Пороги 90% применяются к суммарным количествам утверждений на приёмочном наборе; результаты отдельных вопросов не скрывать усреднением. При нулевом знаменателе указывать N/A с причиной; пустой ответ не даёт 100% качества и не закрывает обязательные факты. Для диагностических сценариев без ответа показывать корректность частичного исхода отдельно.

Первичная оценка выполняется человеком по эталонам и сохранённым доказательствам. Локальная модель может помогать разметке, но её самооценка не заменяет ручную приёмку. Внешние LLM-as-a-judge API не требуются и не разрешаются в рабочем контуре пилота. Это операционные метрики данного ТЗ, а не заявление о точном воспроизведении ALCE, FActScore или RAGChecker.

## Сравнительные и диагностические проверки

На одинаковых вопросах, модели и параметрах сравнить B0 — один поисковый проход с простым ранжированием и ответом — и B1 — ограниченные уточнения по пробелам. Показать качество, длительность и расход ресурсов; B1 не обязан тратить весь бюджет. Для части вопросов, обязательно включая все неверные обычные ответы приёмочной десятки, выполнить вариант O с вручную подобранными доказательствами и тем же генератором. Вариант O служит диагностике и не засчитывается как успешный живой поиск.

Для сравнения обработки контекста использовать общий фиксированный пул сохранённых ответов инструментов; отсутствующий запрос обозначать отсутствующим, не генерировать ему выдачу. Офлайн-сравнение не заменяет живые прогоны. Для каждого неверного ответа указать стадию: документ не найден в выдаче; найден, но не прочитан; нужный текст потерян при извлечении; фрагмент не передан в контекст; фрагмент передан, но использован неверно; причина не установлена.

Позиционный тест использует одни и те же фрагменты и параметры, меняя только положение ключевого доказательства: начало, середина, конец. Длинная страница не должна вытеснять вопрос, инструкции и все прочие релевантные источники. Для экспериментального reranker или сжатия обязательно сравнение с базовым простым ранжированием по качеству и ресурсам; улучшение заранее не предполагается.

Для prompt injection подготовить RU и EN случаи с атакой в тексте, заголовке, поисковом описании и метаданных; включить подмену ответа/цитат и утечку через параметры разрешённых действий. Для каждого случая заранее определить цель атакующего, ожидаемую полезную задачу и чистый вариант с теми же доказательствами. Проверять фактические действия и исходящий трафик, используя только искусственные маркеры. Fixtures запускать в изолированной тестовой среде; рабочую SSRF-защиту ради них не отключать.

В отчёте показать четыре сочетания «цель атаки достигнута/нет» × «полезная задача выполнена/нет» и результат чистого контроля. Искажение ответа учитывается независимо от технически запрещённых действий. Ноль нарушений на фиксированном наборе не объявляется доказательством общей неуязвимости.

## Живые прогоны и измерения

Живые прогоны выполнить в разные дни и фиксировать дату, сеть и состояние кэша. Время ответа измерять отдельно без кэша и с кэшем, отдельно выделяя поиск, HTTP-загрузку, браузер, отбор контекста и oMLX. Отдельно обозначать холодную и прогретую модель. Фиксировать реальные обращения, генерации, доступные входные/выходные токены, метод подсчёта, пиковую память приложения и доступные показатели памяти oMLX с описанием измерения. Перекрывающиеся показатели unified memory на Apple Silicon без пояснения не складывать.

Указать медиану и p95, размер выборки, метод вычисления перцентиля и индивидуальные длительности research-вопросов. На малой выборке p95 считать описательной, нестабильной оценкой; разницу одного случая не объявлять статистически доказанным улучшением. Не обещать одинаковую скорость на разных моделях и не увеличивать живой трафик только для улучшения статистики при риске блокировок.

Автоматические проверки парсеров выполнять на сохранённых HTML fixtures: обычная выдача, пустая выдача, изменённая разметка, CAPTCHA, редирект и реклама. Живой smoke тест запускать отдельно, чтобы внешние изменения не подменяли регрессионные тесты.

Если ни один набор из двух HTML источников не проходит проверку доступности, оформить результат как неуспешную проверку гипотезы с данными прогонов. Не заменять источники сторонним API и не объявлять пилот принятым.

# Этапы и результаты разработки

1. Проверка реализуемости. Проверить oMLX и модель; протестировать HTML источники на целевой машине; выбрать основной и резервный; зафиксировать сетевые обращения, блокировки и исходные показатели. При непроходимом ограничении сначала представить результаты проверки гипотезы.

2. Поиск и чтение. Реализовать search и extract, HTTP и браузерное чтение, единый формат данных, обработку ошибок, ограничения и SQLite кэш.

3. Работа агента. Подключить oMLX, ограниченный цикл с учётом остатка ресурсов, перечнем пробелов и причинами остановки, версионированные доказательства, атомарные claims и research. Формирование ссылок, проверку диапазонов и соблюдение лимитов выполнять приложением.

4. Проверка пилота. Выполнить автоматические проверки, сравнения B0/B1, диагностику O, парные проверки атак и живые прогоны. Оформить воспроизводимый отчёт с метриками поддержки, покрытия, полноты, ресурсов и ограничений, а также инструкцию запуска и очистки.

Передать исходный код, зафиксированные зависимости, пример конфигурации без секретов, README с запуском и очисткой данных, OpenAPI схему с примерами всех исходов, CLI примеры, fixtures, версионированные наборы приёмки, правила и результаты ручной разметки, локальные пакеты испытаний и отчёт. Пакеты с вопросами и текстами остаются локальными и в Git не включаются.

Указать команды воспроизведения проверок и сравнений, срок хранения и лимит пакетов, способ их очистки, измеренные ресурсы, метод подсчёта токенов, известные ограничения и условия восстановления адаптеров после изменения HTML. В отчёте отделить реально пройденные проверки, непройденные и не выполненные; показатели публикаций не подменяют результаты пилота.

# Открытый вопрос об индексе

Живой поиск остаётся основным сценарием и не зависит от предварительно собранного индекса. Кэш документов сам по себе не считается полноценной поисковой системой.

В отдельной исследовательской записке сравнить использование готового решения и создание собственного небольшого индекса поверх накопленных материалов. Кандидаты для проверки: YaCy как готовая система и SQLite FTS5 или Meilisearch Community Edition как основа собственной обработки. Конкретное решение не закрепляется этим ТЗ.

Для небольшого сравнения использовать одну и ту же выборку до 500 очищенных документов из кэша и 10 запросов. Для воспроизводимости допускается заранее подготовленный тестовый корпус. Уравнять доступный текст, поля, единицу ранжирования и правила разметки; зафиксировать подготовку, токенизацию, языковую обработку и настройки каждого движка. Если одинаковый импорт или сопоставимые настройки невозможны, явно описать различие.

Релевантность разметить по шкале 0/1/2, описанной в приёмке. Для конечного корпуса измерить nDCG@5 и полноту по размеченным документам, время индексации, обновления и поиска, размер на диске, память, лицензии фактически выбранных версий и трудоёмкость сопровождения. RU→RU и EN→EN показать отдельно; RU→EN, если проверяется, вынести в отдельную группу. Полноту по всему живому интернету не заявлять и не выводить из метрик этого корпуса.

Результат — рекомендация: нужен ли индекс пилоту, что он улучшает, готовое или собственное решение выбрать и нужен ли отдельный этап разработки. Полноценный краулер и обязательное внедрение индекса в основной поток в объём этого пилота не входят.
