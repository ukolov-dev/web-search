# Локальный MCP: дополнение к ТЗ 1.3

## Bounded research — 5 ноября 2026

6 ноября проверка ответа уточнена: плохие citations отбрасываются по одной, оставшиеся точные witnesses проходят прежний отдельный semantic audit. Непригодные/невидимые chunks, ноль witnesses, неизвестные facets и несоответствие document_version по-прежнему блокируют claim. Числовые массивы и индексы (`[1, 2]`, `a[0]`) разрешены; Markdown links/reference labels и HTML не разрешены. Это ограниченный синтаксис технического текста, не универсальный Markdown-парсер. Audit сохраняет все фрагменты, видимые draft, и конфликтный карантин; если полный контекст не помещается, ответ удерживается.

Для вопроса с RFC, атрибуции RFC в claim или цитирования chunk с RFC применяется строгая первая версия: `RFC N: ` и дословная завершённая клауза соответствующего прочитанного первичного документа. Приложение проверяет конечный официальный URL документа и его собственный номер в заголовке/тексте; `/info/rfcN` и чужое упоминание стандарта не доказывают норму. В отображаемом claim сворачиваются только пробельные разделители, исходная цитата и Unicode offsets сохраняются точно. Клауза остаётся на английском и в русском ответе; пересказ/неполная клауза удерживается. Semantic audit дополнительно проверяет смысл и применимость; это не универсальная проверка истинности.

При RFC-запросе найденные официальные RFC Editor `/info/rfcN` и Datatracker `/doc/rfcN` адресуются к тексту того же RFC внутри прежнего бюджета чтений. Новый адрес повторно проверяется на `site:`; ограничение на `/info/` не расширяется. Приоритет получает запрошенный номер. Публичные URL/DNS/IP/redirect/refusal guards сохранены. Модели явно передаются `facet_indices` с нуля; неизвестные индексы не перенумеровываются и не принимаются. Прежние лимиты, public input schemas, Qwen slots и запрет кэширования verdict/final answer не менялись. [Проверки и ограничения 6 ноября](research-gates-2026-11-06.md). Продолжение: для явного RFC-вопроса внутренний draft выбирает исходные Unicode ranges, Rust копирует exact quote; полный quoted subject допускается без ослабления primary/semantic gates. [Изменения и ограничения 13 ноября](research-followup-2026-11-13.md).

В MCP добавлен пятый инструмент `research`. Предыдущие четыре input schema сохранены. Нужен тот же доверенный startup provider, что для `ranked_search`; `--reranker-settings` вместе с `--evidence-memory` подключает локальный Qwen. При отсутствии Qwen используется ограниченный лексический отбор; при его ошибке последующие попытки Qwen в этом запросе отключаются, поскольку отмена HTTP не гарантирует остановку серверного вычисления.

```json
{"question":"При HTTP 301 может ли клиент заменить POST на GET, а при 307 сохранить метод?","language":"ru","cache_mode":"prefer"}
```

`question`: 1..2000 непустых Unicode code points; `language`: `auto` (по умолчанию), `ru`, `en`; `cache_mode`: `prefer` (по умолчанию), `refresh`. Неизвестные поля запрещены. Модель, ключи, provider URL, пути, лимиты и capture нельзя передать аргументами инструмента. Refresh переоценивает HTTP-тела в task-local scope; идентичное тело допускает переиспользование извлечения/Qwen. Генеративный ответ и verdict не кэшируются.

Один request-local контроллер владеет общим бюджетом: **2 поисковые формы, 4 логических SERP-попытки, 4 попытки чтения документов, 4 Qwen-попытки, 6 генеративных попыток и 180 секунд**. Ошибки и cache hits расходуют логические допуски. HTTP-переходы и кэш отдельно видны в диагностике; каждый сетевой redirect проходит общий guard, максимум5. Нет вложенных `ranked_search`, сброса лимитов по раундам, браузера или стороннего search/scrape API. Отказы источников обновляют общий guard сразу и сохраняются через доверенный `--source-state`. Сохранение ledger при рестарте требует того же файла.

Планировщик выделяет до4 аспектов и первую форму. Rust читает до2 кандидатов и отбирает до3 исходных фрагментов на документ. Черновик предлагает до4 атомарных утверждений; неверные/неизвестные цитаты, ссылки в тексте утверждения и вывод без rationale не выпускаются. Некорректное утверждение отбрасывается, поиск может продолжиться. Отдельная генерация проверяет поддержку **всего** утверждения, ограничения и конфликты. Только принятую ею и структурно валидную часть Rust собирает в `answer`. Незаполненный аспект может вызвать одну уточнённую форму либо дочитывание очереди; поиск разрешено сузить безопасным site:, а исходное ограничение пользователя нельзя расширить; новое свидетельство требует повторного аудита. Одна общая schema-repair попытка входит в6, до неё сохраняется резерв для финального audit. Последние20с не расходуются на новые чтения/черновик. Semantic audit может ошибиться; это прямо обнаружено в предварительной HTTP-пробе.

`sources[].eligible` означает допуск прочитанного тела к рассмотрению, а не доказанную релевантность или истинность. Ответ содержит `request_id`, `status`, `stop_reason`, `answer`, `claims`, `sources`, `facets`, `missing`, `conflicts`, `sufficiency`, `query_forms`, `budget`, `actions`, краткие usage/cost и cache diagnostics. `status`: `ok`, `partial`, `empty`, `error`; остановки: `evidence_sufficient`, `no_new_evidence`, `sources_unavailable`, `budget_exhausted`, `deadline`, `model_error`, дополнительно `cancelled`. `ok` требует всех аспектов, положительного отдельного аудита, отсутствия активных конфликтов и двух разных цитируемых тел документов; независимость издателей не доказана. Одинаковые тела по разным URL не дают второго документа. Вызов MCP cancellation прекращает контроллер, сохраняет пригодные сведения об уже прочитанных источниках и освобождает busy; ранее запущенное удалённое вычисление может продолжаться.

В `claims[].evidence` приложение подставляет `source_id`, `chunk_id`, `document_version`, `field=text`, точную `quote`, `start`/`end` в **Unicode code points исходного извлечённого текста**. Это другая система смещений, чем normalized UTF-8 bytes старого `ranked_search`. `answer_start`/`answer_end` выделяют ровно `claim.text` в готовом `answer`, без добавленного суффикса ссылок. `document_version` связывает URL, SHA-256 исходного текста, metadata и версию обработчика. URL и Markdown-ссылки строит приложение. Метаданные публикации отдельно содержат собственные date witnesses; они не доказывают время события.

Для news используется окно **исходного вопроса**, собственная типизированная Article/date и прежние проверки дат; Feed→article — только реальная ссылка того же origin, загрузка Feed расходует тот же документный бюджет. Ленты, приложения и статьи с неверными/неизвестными датами не становятся фактическими свидетельствами. Это не qualification всего новостного поиска.

Публичный structured JSON и дублирующий его MCP text каждый ограничены32KiB UTF-8. Полные тела, все scores Qwen и raw model calls возвращаются только в явном trusted capture. При переполнении сначала убирается диагностика, затем ответ удерживается целиком и выставляются `partial`, `output_limited`; некорректные обрезанные цитаты не возвращаются. У MCP wire есть стандартное дублирование text/structured, поэтому его суммарный размер может быть больше32KiB. В одном изолированном Harness-прогоне spill не было; гарантий для всех клиентов нет.

Тот же контроллер доступен через CLI (все пути — доверенные локальные настройки):

```sh
target/release/web-search research "Ваш вопрос" \
  --openrouter-key-file "$KEY_FILE" --model "$MODEL" \
  --openrouter-proxy http://127.0.0.1:10808 \
  --reranker-settings "$RERANKER_SETTINGS" --source-state "$SOURCE_STATE" \
  --cache-db .cache/research.sqlite --language ru --live
```

Альтернатива OpenRouter — уже поддержанный локальный `--settings PATH`. `--capture-dir` требует пустого каталога; `--output` сохраняет публичный JSON. Без `--live` CLI ничего не запрашивает. Уже работающий MCP-процесс нужно перезапустить для discovery нового инструмента. Пользовательские глобальные настройки Harness этим изменением не редактировались. [Проба, корпус и ограничения](research-mvp-2026-11-05.md).


## Локальный кэш — 5 ноября 2026

`mcp --cache-db PATH` явно включает приватный SQLite-кэш публичного HTML, извлечённого текста и оценок локального Qwen. Без флага поведение остаётся прежним. Это принятое пользователем дополнение к ограничению v1.3, где полный HTML допускался только в диагностическом режиме. Путь и режим задаёт доверенный startup, не аргументы MCP. Ключи, cookies, настройки авторизации, генеративные ответы и verdicts в кэш не записываются.

Начальные максимальные TTL: выдача — 15 минут, документы — 24 часа; новостное чтение и распознанные Article/Feed ограничиваются 5 минутами, в том числе при чтении прежних записей с более широким TTL. Консервативный Feed-detector может также сократить TTL главных/поисковых страниц. `Cache-Control: no-store`, `no-cache`, `max-age`, `Age` и `Vary: *` могут сократить повторное использование. Клиент не принимает/не отправляет сессионные cookies. На просроченной записи требуется HTTP; при наличии валидаторов передаются ETag/Last-Modified. `--cache-refresh` требует `--cache-db` и принудительно проверяет тела через HTTP. При 304 сохраняются тело, его хэш и `fetched_at`, обновляются `checked_at`/`expires_at`; идентичное тело позволяет переиспользовать извлечение. Ошибки, parser failures и challenge не записываются как успешные страницы; stale fallback при ошибке отсутствует.

Ключ HTML сохраняет схему, хост, порт, путь и query; фрагмент исключён. Ключ текста включает конечный URL, SHA-256 HTML и версию извлекателя; Qwen — endpoint/model ID, запрос, точные входные фрагменты и версию обработчика. При замене checkpoint под прежним model ID нужно очистить кэш. При изменении извлекателя/HTTP-заголовков/формата оценки разработчик обязан повысить соответствующую версию ключа. Каждый blob проверяется по SHA-256. TTL не доказывает актуальность факта; новостное окно и coverage/audit пересчитываются при каждом вызове.

Перед выдачей HTML из кэша снова проверяются публичные URL, все сохранённые redirect hops, блокировки хостов и DNS/IP. Сетевой ответ дополнительно сохраняет прежнюю проверку peer IP. `cache` содержит счётчики фактических HTTP/Qwen/extraction операций, hits/misses/writes/errors; hits включает прочитанные записи для conditional validation, поэтому не равно числу сэкономленных HTTP. У извлечённых документов и прочитанных ranked-страниц есть `source_cache` с исходными временными метками. `document_http_status=200` может относиться к сохранённому успешному ответу; живое обращение в этом вызове определяет `cache.http_reads`.

Полезные payloads ограничены 480 МиБ, запись — 8 МиБ, количество — 10000; удаляются сначала просроченные, затем LRU. SQLite использует WAL/FULL, ограничение числа страниц и checkpoint; это не измерение пикового общего места с WAL/временными файлами. На один путь базы допускается один MCP-процесс, внутри него сохраняется один активный инструмент с `busy`. Межпроцессная очередь/singleflight для будущего VPS не реализована. Ошибка отдельной операции кэша отмечается в stderr/`cache.errors`, поиск продолжает обычное чтение; чужая/нечитаемая база и второй владелец отклоняются при startup.

Очистка не требует LLM или сети:

```sh
target/release/web-search cache-clear --cache-db .cache/web-search.sqlite --url https://example.org/article
target/release/web-search cache-clear --cache-db .cache/web-search.sqlite --all
```

Очистка URL удаляет его HTML и все производные text/Qwen-записи: это консервативная очистка зависимостей, без сложного графа. Сам файл базы остаётся. Параллельно с владельцем очистка отклоняется.

`--source-state PATH` отдельно сохраняет только отказы поисковиков/хостов между последовательными перезапусками. Существующее состояние не сбрасывается из-за cache miss/refresh. `--capture-dir NEW_OR_EMPTY_DIR` явно сохраняет диагностические HTML/model-call snapshots; предел проверяется перед каждым вызовом (512 МиБ плюс один ограниченный вызов). Непустой каталог отклоняется. Это диагностические файлы, их очистка отдельна от `cache-clear`.

`ranked_search.usage` сообщает число generative calls, сумму известных `reported_cost_usd`, `cost_complete` и `unknown_cost_calls`. При неизвестной стоимости сумма — нижняя граница. Это стоимость внутренних модельных запросов; расход самого Harness/другого агента считается отдельно. Результаты живого сравнения: [Harness NEW20 и кэш](harness-cache-2026-11-05.md).

## Новостной путь от 3 ноября 2026

Текущий opt-in `--evidence-memory` использует `request-evidence-v14-news-anchors`. Для запроса с новостным намерением `ranked_search` может прочитать найденную ленту и до трёх статей по её реальным same-origin ссылкам. Лента входит в общий предел четырёх HTTP-чтений; прочитанные статьи повторно не загружаются для Qwen/coverage/audit. Сохраняются три генеративных вызова, четыре Qwen-вызова, 180 секунд и 24000 символов source JSON на модельный вызов. Default legacy сохранён.

Новостной `direct` требует прочитанную отдельную статью, полную дату публикации, соответствие календарному окну и прежние coverage/audit/witness проверки. Для «сегодня»/«вчера» берётся соответствующий день Europe/Moscow; поддержаны явные день/месяц/год и месяц/год; без периода — последние три календарных дня. Неоднозначные/неподдержанные диапазоны, дата без года, конфликт дат и будущее остаются недоказанными. Дата события, `dateModified`, copyright и соседний teaser не заменяют дату публикации. Это проверка публикационного периода, не актуальности всех фактов или даты будущего мероприятия.

Ответ содержит `news_navigation` с окном, фактическими чтениями и parent→article ссылками; у результатов `news` с исходными свидетельствами даты и причиной допуска/отказа. `extract` также возвращает `news` с типом и датой/unknown, без привязки к запросному окну. Свидетельства публикационной метадаты в coverage имеют отдельное поле `publication_date` и ID `D1…`; дата не может быть core-доказательством. Доверенное календарное окно передаётся модели отдельно от веб-текста.

Страница скачивания приложения не является прямым ответом на запрос новостей. Явные запросы приложений/скачивания сохраняют свой смысл, а новость о выпуске приложения не отвергается только за слово «приложение». Фильтр не является полным классификатором всех магазинов. Навигация использует ограниченный отбор URL/заголовков; подходящие статьи могут не попасть в четыре чтения. Новые возможности не квалифицируют v13 для общего default-поиска; навигация и даты описаны в [отчёте v11](news-navigation-2026-11-03.md), текущая проверка coverage — в [отчёте v12](news-coverage-2026-11-03.md).

В v12 coverage сохраняет четыре поля checks, но неиспользуемые поля после core и объявленных anchors при валидном доверенном новостном окне канонизируются в `missing/[]/""`. Для лишнего `supported` обязательны точные собственные snippet/body/publication_date-свидетельства; противоречия, heading-only и некорректные ссылки остаются ошибкой. Лишние поля не доказывают обязательных условий. Диагностика — `witness_rejections[].reason=ignored_unused_news_check`. Новостная coverage-подсказка требует содержательную body-цитату вместо повтора заголовка; активные условия и полный semantic audit сохранены. Неновостной путь не меняется.

В v14 публикационная microdata берётся из единственной основной Article, которой принадлежат единственный глобальный h1 и собственные URL/идентичности, даже если на странице есть sibling-анонсы. Вложенные/чужие сущности и их даты не заимствуются; Event/modified/неполные/conflicting/future даты сохраняют отказ. Для явно размеченной собственной Article тот же scope применяется к `extract` перед широким main: `extraction_method=owned_article`, `content_scope=article`; вложенные news-статьи исключаются из body. News-only guidance coverage/audit требует связи события с запрошенным городом, которую не заменяют издатель/область/чужой teaser; конкретный городской маршрут или учреждение допустимы. News coverage не тратит anchors на слова типа «новости»/«свежие», когда они лишь задают тип/доверенное окно запроса; полный запрос и все фактические условия обязательны. Собственный фактический главный заголовок может подтвердить non-core место того же события вместе с содержательной body-цитатой; core сохраняет S/B и запрет повтора заголовка. Активный missing по-прежнему блокирует direct, parser repair не расширен. Неновостные prompts и бюджеты не меняются. Реальные development-ошибка и новый набор описаны в [отчёте v14](news-dates-2026-11-03.md); общая квалификация не заявляется.

Решение от 28.10.2026 по обсуждению с пользователем: основной интерфейс для агента — MCP. Сначала проверяется локальный stdio. Для будущего удалённого режима рассматривается Streamable HTTP; VPS, удалённая аутентификация и REST сейчас не реализуются. Общие ограничения и требования к качеству из ТЗ 1.3 сохраняются. Это дополнение описывает текущий экспериментальный интерфейс, а не приёмку полного пилота.

Используется официальный [Rust MCP SDK](https://github.com/modelcontextprotocol/rust-sdk), crate [rmcp 3.8.0](https://docs.rs/rmcp/3.8.0/rmcp/). Версия закреплена в Cargo.toml/Cargo.lock; сервер использует transport-io, клиент для тестов — transport-child-process. CLI и MCP вызывают одни функции поиска и извлечения.

## Контракт текущей пробы

| Инструмент | Вход | Выход |
| --- | --- | --- |
| search | query: непустая строка до 2000 Unicode code points; engine: bing, ddg, mwmbl, seznam или naver, обязателен; max_results: 1..10, по умолчанию 5 | status=ok/partial/empty/error, engine, результаты с title/url/snippet/position, время, предупреждения; при сбое isError=true, error_code и текст error |
| ranked_search | query: непустая строка до 2000 code points; max_results: 1..10, по умолчанию 5 | status=ok/partial/empty/error, results с id/url/title/snippet/classification/evidence/rrf_rank, document_http_status и requirement_evidence; page_verification с документными ошибками и числом повышений; forms, ошибки и фактические бюджеты. Без startup-настроек model_unconfigured. Метки direct/background/irrelevant — предсказания релевантности, не проверенные факты |
| discover | url: публичная HTML-страница до 4096 code points; query: непустая тема до 2000 code points; max_links: 1..50, по умолчанию 20 | status=ok/empty, url/final_url/hops, query, scope_origin, source_html_hash SHA-256, links с url/label/position/lexical_matches, candidates, truncated, elapsed_ms; при сбое status=error, isError=true, error.code=discovery_failed |
| extract | urls: массив из 1..8 публичных HTTP(S) URL до 4096 code points каждый | status=ok/partial/error, documents; по успешному документу text, title, text_hash SHA-256, chars, blocks, truncated, url, final_url, hops, elapsed_ms; по неуспешному url/status/error |

Все входные объекты отклоняют неизвестные поля. Пустой запрос, выход за численные лимиты, неверный engine и небезопасные адреса не запускают загрузку. Синтаксические/типовые ошибки параметров SDK может возвращать как tool result с isError=true; явные проверки обработчика возвращают JSON-RPC invalid_params. Неизвестный инструмент отклоняется. Клиент должен обрабатывать оба вида ошибки, а не только исключение транспорта.

extract сначала проверяет весь массив URL, затем загружает их последовательно. Ошибка одного публичного документа не уничтожает успешные: status=partial, isError отсутствует/false. Полный провал: status=error, isError=true. HTTP 404 не превращается в успешно прочитанный текст. Все успешные данные помечены untrusted_content=true; предупреждение в initialize и описаниях инструментов требует считать содержимое сайтов данными, а не инструкциями. Это не доказательство устойчивости агента к prompt injection.

Внутри MCP-процесса допускается один активный инструмент; параллельный вызов получает isError=true с error.code=busy. После CAPTCHA/HTTP 202/403/429 поисковый адаптер отключается до перезапуска процесса. Заблокированные хосты целевых страниц также запоминаются в MCP-процессе между ranked_search/discover/extract. Автоматических повторов, обхода блокировок и подмены источника нет. HTTP-клиент сохраняет ограничения размера, времени, редиректов и проверки публичных DNS/IP из проб первого этапа.

## Уточнение надёжности от 28.10.2026

Поддерживается один незаключённый в кавычки оператор `site:domain[/path]`, включая регистр `SITE:`. Фильтр допускает точный хост и его поддомены; для пути — сам путь и вложенные сегменты. Похожие домены и соседние префиксы пути не подходят. Схема HTTP/HTTPS результата не ограничивается схемой нормализации site-фильтра. Ограничение проверяется локально после нормализации результатов, одинаково для CLI и MCP.

Если отброшена часть результатов, status=partial, discarded_results содержит их число, предупреждение сохраняется. Позиции исходной выдачи не перенумеровываются. Если все непустые результаты нарушают фильтр — status=error, isError=true, error_code=source_query_mismatch, results=[]. Это отказ источника соблюдать запрос, а не утверждение об отсутствии страниц во всём интернете. Явная пустая выдача имеет status=empty без isError=true.

Пустой site, несколько site, OR с site, -site, wildcard, скобки вокруг site, незакрытые кавычки, userinfo, локальная цель, нестандартный порт и query/fragment внутри site отклоняются до сетевой загрузки. Полный язык операторов поисковика не реализуется; текст site внутри целиком заключённой в кавычки фразы считается буквальным текстом.

Коды captcha/source_challenge/source_blocked/rate_limited/source_policy_changed отключают источник в текущем процессе. Слова из пользовательского запроса или URL ошибки не считаются кодом блокировки. source_query_mismatch и invalid_query не отключают источник для остальных корректных запросов. Валидация query может возвращать structured tool error; оба вида MCP-отказа, описанные выше, остаются допустимыми.

Mwmbl читает HTML без JS и без включения Seed Search. Метки Mwmbl/Wikipedia явно разрешены и возвращаются как result_source; EUSP и неизвестные метки отклоняются. Это контроль наблюдаемого HTML, а не аудит внутренних обращений стороннего сервиса. Источник остаётся экспериментальным: его предварительная оценка — 2/20 на текущем наборе. Автоматический fallback не добавлен; агент выбирает engine явно.

Процесс не открывает серверный сокет, не запускает Chromium, не сохраняет полученные страницы на диск и не предлагает агенту чтение файлов, shell или изменение конфигурации. Без `--omlx-settings` настройки модели не читаются; с этим явным startup-параметром ключ собственного oMLX читается в память для ranked_search и не попадает в результаты. Вывод stdout занят протоколом. CLI сохраняет отдельные диагностические команды с явно переданными параметрами.

## Навигация по заданному корню: discover

Дополнение от 28.10.2026 по результатам [исследования](search-reliability-research-2026-10-28.md). Это одна загрузка HTML через общий безопасный HTTP-клиент и разбор вне сетевого event loop: до 5 МиБ, до 50 тысяч DOM-элементов, без JavaScript и обхода найденных ссылок. Редиректы загрузки могут идти на другой публичный origin и проверяются общим клиентом; возвращаемые ссылки ограничены точным origin **конечной** страницы (схема, хост, порт). Поддомены и похожие домены автоматически не включаются. Начальный URL задаёт вызывающий; инструмент не доказывает, что это официальный сайт.

Учитывается первый HTML base[href]. Относительные ссылки разрешаются по нему; если base указывает на другой origin, относительные внешние кандидаты отбрасываются. Отбрасываются userinfo, недопустимые схемы и локальные литералы; DNS найденной ссылки проверяется только при последующей загрузке extract. Фрагменты снимаются, повторы URL и ссылки на текущую страницу исключаются; query сохраняется. position — исходный номер a[href] в документе. label ограничена 500 символами. В число candidates входят уникальные допустимые ссылки до ограничения max_links; truncated сообщает об отсечении списка.

Порядок определяется числом общих слов темы и подписи/пути URL; учитываются Unicode буквы/цифры, слова длиннее одного символа, без морфологии, перевода и синонимов. Равные оценки сохраняют порядок документа. query здесь является темой навигации, не синтаксисом search/site. Нулевой или высокий lexical_matches не означает бесполезность или достоверность. Подписи, URL и остальной контент остаются недоверенными.

Загрузка seed считается одним документом в плане агента; редиректы отдельно видны в hops. Проба навигации ограничена seed + двумя страницами. Общий лимит восьми URL между произвольными отдельными вызовами MCP пока не обеспечивается сервером: централизованный бюджет будет частью research. Сам discover рекурсивно ничего не загружает. Коды блокировки поискового engine сохраняются только для search; discover после ошибки не выполняет автоматических повторов, но отдельного постоянного состояния блокировки хостов у него нет.

Проверка достаточности локальной моделью и экстрактивный фильтр выдачи существуют только как явно запускаемые Rust-пробы, исключённые из release-бинарника. Новый LLM-инструмент в MCP не опубликован. Результаты и ограничения — в [отчёте](docs-evidence-probe-2026-10-28.md).

## Ranked search: B17, 29.10.2026

Запуск: `web-search mcp --omlx-settings "$HOME/.omlx/settings.json"`. Необязательный `--model` задаёт установленную локальную модель. Файл должен принадлежать доверенной локальной конфигурации; разрешён только loopback, без proxy/redirect/retry. Без этого параметра остальные три инструмента работают как прежде, а ranked_search возвращает model_unconfigured. Ключ и путь к настройкам не передаются инструменту и не возвращаются агенту. Глобальные конфиги клиентов автоматически не изменяются.

Для исходного калибровочного набора используются фиксированные формы из feasibility/b17-policy.json; новые запросы выполняются в исходной формулировке. Изменение форм по результатам этого прогона не выполнялось. Нет автоматического LLM-rewrite, определения авторитетности или вызовов внешних API.

На вопрос: максимум 4 формы × 2 HTML-источника (Seznam/Naver), 8 логических SERP, 3 классификации всех ID, 24000 Unicode code points входного контекста на вызов, 180 секунд на retrieval/classification после отдельной проверки доступности модели (до 15 секунд). Рекомендуемый timeout клиента — 210 секунд. Это локальный бюджет одного ranked_search; общего бюджета между search/discover/extract ещё нет. В CLI suite одинаковые engine/query дедуплицируются в памяти одного прогона; MCP-вызовы не используют межвызовный кэш.

Кандидаты: канонизация и дедупликация URL, ограниченные title/snippet, classify-all по JSON schema, затем direct-first и свежий RRF. С 29.10 classifier conservative-evidence-v2 требует для direct дословную цитату 16..160 символов из title либо snippet; Rust проверяет её после нормализации whitespace. Отсутствующая/выдуманная цитата понижает direct до background и даёт partial с grounding_downgrades. Цитата доказывает происхождение текста, но не его смысловую достаточность. Дополнительно проверяются буквальные API/идентификаторы (CamelCase, snake_case, составные заголовки, аббревиатуры), числа/версии и явно заданный месяц. Несколько HTTP-кодов допускаются как альтернативы, кроме сравнительного запроса. Есть EN/RU названия месяцев и ISO/Korean числовая запись. Отсутствующий якорь понижает direct до background; это консервативный фильтр, а не понимание смысла. Синонимы и обрезанные сниппеты могут приводить к пропуску полезных карточек. Полный отчёт: [новый набор и извлечение](relevance-extraction-fix-2026-10-29.md). Более 72 кандидатов или превышение контекста не разрешают молча отбросить ID: классификация отклоняется, status=partial, classification=null и остаётся RRF. Внутренний JSON-ответ модели — объект labels с обязательным ключом каждого ID и значениями kind/evidence; повторные/неизвестные/пропущенные ID отклоняются. Неполный/невалидный ответ модели также сбрасывает все метки; повторов/ремонта формата нет. Текущий classifier v4: initial max_tokens4096 и reasoning none только для точного pinned DeepSeek, для остальных initial2400 без override; отдельные coverage/audit limits указаны ниже. Прочие бюджеты сохранены. Модельные Warning сохраняются в errors. Финальный локальный site-фильтр применяется до top10; diagnostic pool/протокол модели не возвращаются MCP-клиенту. Naver использует один последний organic anchor text и для title, и для snippet: это не verified headline. Отсутствие source errors и classifier_valid не доказывает качество результатов.

Целевые документы ranked_search не читает: document_http_status=null, fetch_method=unknown, document_reads=0. Для проверки содержимого агент явно вызывает extract. Полный research, evidence sufficiency и защита фактического ответа не включены. Полные локальные capture сохраняются только в явно указанном новом каталоге CLI ranked-suite/ranked-search; существующий каталог не перезаписывается.

## Уточнение extract: semantic content и объём

Исправление от 29.10: единичный main/role=main или article берётся из исходного HTML до эвристического Readability. Для научной страницы с citation_title приоритет имеет явно размеченное article-body/role=doc-body, затем abstract (включая языковые варианты); иначе остаётся Readability. Навигация, scripts, скрытые элементы и кнопки убираются. Выбранное поддерево сериализуется один раз, включая текст div, pre и таблиц, без повторов вложенных p/li. blocks теперь считает непустые текстовые блоки, разделённые двойным переводом строки; это не DOM node count. Лимиты 5 МиБ HTML / 50000 DOM elements / 100000 code points текста сохраняются.

Ответ дополнен extraction_method, content_scope, coverage=not_verified, warnings, available_fulltext_url. abstract_only означает, что возвращено резюме, не полная статья. Полная статья из metadata возвращается как URL после синтаксической проверки; DNS/IP проверяются при фактическом чтении, но автоматически не читается: её нужно явно передать следующему extract и учитывать как ещё одну загрузку. coverage=not_verified и truncated=false не означают доказанную полноту страницы. Ограниченный корпус regression fixtures не квалифицирует извлечение всех сайтов. Все новые поля проходят через тот же CLI/MCP extract; settings/сеть/JS не добавлены.


## Ограниченное восстановление recall от 29.10.2026

После консервативной SERP-классификации ranked_search читает до четырёх background-кандидатов в порядке RRF через общий безопасный HTTP/extract. Это максимум четыре попытки чтения документов, включая ошибки, отдельно от 8 логических поисковых вызовов. Site-фильтр проверяется до загрузки и по конечному URL. Браузер, рекурсивный обход и повтор после блокировки не добавлены.

Из текста выбираются до двух непрерывных фрагментов по 1200 code points без строк оглавления с точечными лидерами. Модель предлагает direct и ID одного из готовых фрагментов; Rust подставляет настоящий текст цитаты и проверяет API/version/date ограничения. Для привязки технологии сохраняется page_title из HTML head, отдельно от основного текста. Цитата должна существовать и в исходном извлечённом тексте: склейка разных фрагментов не считается доказательством. Второй вызов модели проверяет реальную помощь вопросу и его ограничения. При ошибке, неполном JSON, неизвестном ID или несогласии повышения нет; исходные SERP-метки сохраняются.

Общий предел — три модельных вызова и 180 секунд для retrieval, чтения и классификации после model preflight до 15 секунд. Если начальная классификация требует больше одного batch, восстановление пропускается ради бюджета. Для повышенной карточки requirement_evidence содержит реальные фрагменты до 1200 символов каждый, их ID, source_url, page_title и SHA-256 text_hash; evidence — первые 160 символов основного фрагмента; document_http_status заполнен только при фактическом HTTP-ответе. fetch_method=http_extract означает успешное извлечение, а не полную или фактически верную статью. Не прочитанные карточки имеют неизвестный документный статус.

Это проверка релевантности источника, не готовности полного ответа. Исходный classifier не ослаблен; страницы с голым упоминанием, неподтверждённой связью или недостающим обязательным аспектом не должны становиться direct. Ограничения и результаты собственного эксперимента: [отчёт recall](recall-body-verification-2026-10-29.md).


## OpenRouter — дополнение 30.10.2026

По явному запросу пользователя ranked_search теперь поддерживает внешний OpenRouter через startup `--openrouter-key-file PATH --model ID`, взаимно исключительно с `--omlx-settings`. Модель и фиксированный endpoint не управляются аргументами инструмента. При этом режиме вопросы, SERP и текстовые фрагменты передаются внешнему LLM; прежние quote/literal guards и бюджеты сохраняются. Ответ содержит model_provider/model. Запуск, защита ключа и границы проверки описаны в [OpenRouter-дополнении](openrouter-2026-10-30.md). Без startup-провайдера ranked_search по-прежнему model_unconfigured.


Исправление доступа 30.10: при уже настроенном локальном HTTPS proxy startup принимает `--openrouter-proxy http://127.0.0.1:PORT`. Параметр разрешён только вместе с OpenRouter key-file; требует HTTP loopback endpoint без credentials/path/query/fragment. Он применяется только к модельному клиенту до запроса. DNS/IP/redirect guards публичных страниц и oMLX не меняются. В текущем окружении явный системный маршрут подтвердил DeepSeek и release MCP smoke; прямой маршрут получал Cloudflare403. Детали в OpenRouter-дополнении.

## Evidence memory: opt-in, 30.10.2026

Default `ranked_search` сохраняет legacy. Исторический этап `request-evidence-v6-context-audit` (последующее текущее поведение описано в начале документа) ввёл под startup-флагом `--evidence-memory`: общий контроль до10 direct/background кандидатов, исходный вопрос R0 и до3 exact query anchors, состояния supported/missing/contradicted/ambiguous с passage IDs, hashes и диапазонами UTF-8 bytes в whitespace-normalized field. До coverage читаются до4 кандидатов; максимум1 слот резервируется для query-overlapping reference URL (docs-host/path), даже с initial irrelevant/boilerplate. URL служит только выбору чтения, не поддержке direct; затем один coverage и skeptical audit всех proposed direct, включая initial SERP-direct. Для каждого supported требования нужна непрерывная цитата16..240 символов из реального passage; core нельзя подтвердить одним заголовком. Некорректная цитата локально становится ambiguous с witness_rejections; неизвестные ID/ссылки и нарушенная schema отвергают batch. Без принятого audit direct понижается до background. Reviewer и audit используют одну модель, не независимую приёмку.

Память ограничена запросом и не является долговременным кэшем или памятью Project Context Router. Public `page_verification.evidence_memory` содержит coverage, пробелы и source references без повторной выдачи всего текста; `requirement_evidence` у direct содержит реальные отдельные цитаты с диапазонами. `evidence` — префикс одного core passage, а не склейка разных частей. Body `text_hash` относится к извлечённому документу, `normalized_text_hash` — к нормализованному полю, по которому отсчитываются ranges. Для title/snippet/hash следует учитывать поле `field`.

Адреса/ключи и режим задаёт доверенный startup, аргументы MCP `evidence_memory` не принимаются. Budget остаётся3 model calls (включая initial classifier),4 target read attempts и180 с после preflight; context<=24000 символов. Для точного pinned DeepSeek initial использует reasoning none/max_tokens4096, coverage6000 и audit2400. Initial других моделей сохраняет2400 без override; для oMLX thinking отключён как прежде. Incomplete/empty output не принимается и не ремонтируется. Короткое имя module.name допускается только при соответствующем настоящем page title; цифры/версии не сокращаются.

Историческая v2: на12 вопросах /201 карточке после body: baseline TP5/FP0/FN13, v2 TP4/FP0/FN14. V2 — development-повтор после разбора ошибки v1, не независимый holdout. Локальная MiMo новым режимом вживую не проверена. [Полный отчёт](evidence-layer-implementation-2026-10-30.md). Это source relevance, не доказательство истинности фактов и не опубликованный research/answer API. VPS и Chromium не включены.

Финальная v4 на другом свежем8/154 с локальным Qwen: initial2/8→8/8, TP1→9,FP0→0,FN15→7, direct recall6,25→56,25%; [полный отчёт с неудачной v3 и ограничениями](reliability-full-search-2026-10-30.md). MiMo+v4 по качеству не проверена.

## Локальный passage reranker: opt-in, 30.10.2026

Дополнительный startup-флаг `--reranker-settings <oMLX settings file>` требует `--evidence-memory` и настроенного classifier provider. Он создаёт отдельный loopback-клиент фиксированной модели `Qwen3-Reranker-0.6B-4bit`. Reviewer может использовать OpenRouter; scoring остаётся локальным. Runtime не скачивает веса и не меняет настройки oMLX. Установленная MLX affine4bit конверсия занимает346774989 байт; oMLX0.7.0 поддерживает её через `/v1/rerank`.

Пул строится из всего whitespace-normalized извлечённого тела (до100000 code points), окна1200 code points с шагом1000, включая хвост; максимум128 окон. Все получают score, затем выбираются до3 окон с перекрытием меньше50% меньшего. В v9 сохраняется rank1 Qwen, остальные выбираются из top6 по покрытию новых query features; lexical features служат только ранжированию. Offsets — UTF-8 bytes исходного нормализованного тела, без переписывания текста. Score не устанавливает direct и не отменяет coverage/literal/site/provenance guards.

С5ноября selector `query-feature-cover-v3-news-lead` дополнительно сохраняет первое1200-char окно извлечённого body для новостных запросов, если его ещё нет в выборе: третий slot заменяется, первые два и сильнейшее окно Qwen сохраняются. Это окно может находиться за пределами top6; `candidate_pool` в trace остаётся preview Qwen top6, а `pool_ranges` содержит весь scored pool. Для технических запросов, download/app selection и tutorial действует прежний отбор. Новых scoring/generative calls и startup/MCP args нет; пределы3body slots/1200chars на slot и все v14 evidence/date/status/audit gates сохранены. [Проверка с Firecrawl на12других страницах](qwen-firecrawl-selection-2026-11-05.md) дала рост сохранности фрагментов, но не direct recall; Firecrawl здесь только тестовый reader adapter.

Предел3 generative model calls остаётся; дополнительно возможны до4 локальных scoring calls, по одному на успешно прочитанную страницу, до30 с каждый внутри того же180 с deadline. `budget.reranker_calls/reranker_pairs` показывают дополнительные операции. `page_verification.passage_reranker` содержит model и bounded traces с индексами, scores, pool/selected ranges, tokens и elapsed time; `status=lexical_fallback` объясняет откат при transport/timeout/invalid response. В таком случае сохраняется прежний lexical selector и последующий общий gate; явная диагностика не означает успешный rerank. No redirects, no proxy, no retry, только trusted loopback settings. В response проверяются model, полный набор уникальных input indices и finite scores0..1.

Для текущего локального запуска:

```sh
target/release/web-search mcp \
  --openrouter-key-file "$HOME/.config/web-search/openrouter.key" \
  --openrouter-proxy http://127.0.0.1:10808 \
  --model deepseek/deepseek-v4.1-flash-1017 \
  --evidence-memory \
  --reranker-settings "$HOME/.omlx/settings.json"
```

Ключи не передаются в аргументах MCP и не сохраняются в отчётах. Для локального LLM можно использовать существующий `--omlx-settings`, но качество связки MiMo+Qwen этим экспериментом не проверялось. Default режима не изменён: [A/B](reranker-2026-10-30.md) улучшил passage coverage, сохранив recall и имеющиеся FP. VPS/API и публичный Chromium не включены.

## Coverage v9: локальные отказы и атомарные условия

`request-evidence-v9-reference-context` сохраняет полный original query в R0. До3 anchors — целые уникальные single-word query tokens; их смысл проверяется в исходном отношении, включая корректный отрицательный ответ. Это не требование истинности предпосылки вопроса. Все direct требуют coverage и отдельный audit; границы3 generative/4 reads/4 Qwen/180с/24k context не изменены.

Title-only core получает ambiguous через прежнюю проверку body/snippet witness; остальные источники той же пачки сохраняют свои проверки. Неизвестные IDs, неподтверждённые passage refs, плохой контракт и незавершённый ответ по-прежнему закрывают соответствующий путь. Evidence-mode audit schema разделяет принятый verdict (`supported=true`, `missing_aspect=""`) и отказ. Runtime validator не ослаблен. Для сравнений требуется source-связь каждой обязательной альтернативы с её эффектом; перечисление имён не подтверждает поведение.

Extraction умеет читать один полный publisher-declared typed code-view файл с совпадающими paths/line count и безопасным escaping. Это не выполнение JavaScript или публичный Chromium. `scope=file_source` и `method=declared_code_blob` не доказывают semantic coverage. Исторический v9 trace reranker содержит selector `query-feature-cover-v2-operation-context`; текущий v3 описан выше. Feature coverage остаётся диагностикой, direct определяется последующими guards.

[Отчёт с неудачным первым вариантом и финальным новым набором](passage-coverage-2026-10-30.md). Default legacy сохранён; никаких новых startup-флагов или адресов/ключей в MCP arguments не добавлено.

V9 дополнительно распознаёт согласованную publisher-declared HTML4 Javadoc class structure (`scope=api_reference`, `method=declared_reference_body`), сохраняя общий100k cap и hash. После Qwen-разметки secondary slots могут быть сдвинуты к сильному exact operation-heading/signature: первый Qwen slot не меняется, длина/UTF8/query features сохраняются, конец ограничивается следующей операцией. Новые spans — postprocess исходных scored windows, не отдельный scoring call.

Финальный audit получает фактическую цитату каждого coverage check. Для pinned DeepSeek используется `reasoning=low`, `max_tokens=6000`, `exclude=true`; initial остаётся `none/4096`, coverage — `none/6000`. Общие3generative/4reads/4Qwen/180с/24k source context сохранены, но response-token budget audit повышен с3200 до6000. Цена и reasoning tokens учитываются в отчёте; reasoning text не сохраняется. [Документация OpenRouter](https://openrouter.ai/docs/guides/best-practices/reasoning-tokens) описывает общий бюджет thinking+visible output; поддержка low у model pin дополнительно проверена публичным GET /models и реальной генерацией.

Known-target conflict с невалидной цитатой блокирует обе названные стороны, но не считается grounded conflict. Валидные дубли пар объединяются; неизвестные IDs/shape/finish по-прежнему fail closed. Некорректная пара не отменяет независимый валидный verdict другого источника. Все опубликованные `audit_conflicts` имеют точные source quotes.

## Document admission и literal bindings v10

`request-evidence-v10-admission-literals` сохраняет v9 coverage/audit и те же бюджеты. Единственный reference reserve выбирается среди подходящих `site:` карточек: qualified API даёт leaf term, `_`/`-` identifiers не разбиваются, URL man-section распознаётся как reference. При равном URL overlap учитывается exact overlap той же карточки. Это даёт возможность прочитать источник и не восстанавливает отвергнутый raw direct.

Literal gate допускает только два ограниченных source-bound соответствия: unquoted JavaScript через явный ECMAScript в том же body passage с subject/core witness; unquoted FD_CLOEXEC через supported exact quote о close-on-exec file descriptor flag, matching requirement и объявленный subject той же страницы. Quoted/backticked имена, namespace, другие flags и headers остаются дословными. Ни одно соответствие не устанавливает direct: сохраняются все coverage checks, source scope/status, provenance, conflict quarantine и отдельный accepted audit.

[Датированный отчёт и больший парный набор](admission-literals-2026-10-30.md). Новых CLI/MCP аргументов, зависимостей и изменений model/reranker/extraction нет.

Core witness, целиком повторяющий фактический page title `H`, получает `ambiguous`, даже если модель сослалась на копию заголовка внутри body. Проверка не применяется к SERP title `T`: адаптер может вернуть там содержательный body teaser. Это консервативный structural guard; смысл остальных цитат по-прежнему проверяет audit.

Лимит24000 символов применяется к source JSON каждого model call. `source_context_max` — максимальный размер такого JSON за запрос, не сумма трёх вызовов; system prompt/schema/output в этот счётчик не входят. Общий межвызовный бюджет ещё не опубликован.

### Research: ссылки для MCP-клиента

Помимо прежнего первого text-блока и неизменного structuredContent, успешный или partial `research` может вернуть стандартные `resource_link`. Они ссылаются только на eligible источники, упомянутые в evidence возвращённых claims, с дедупликацией по точному URL. Некорректные/локальные URL и нецитируемые источники не добавляются. Имя берётся из ограниченного заголовка либо hostname. Дополнительных HTTP/DNS/model вызовов нет: ссылки используют уже полученные документы.

Блок ссылки не является новым доказательством истинности и не меняет результат semantic audit. Ошибки и пустые claims не получают ссылок. Ссылки добавляются только пока сериализованный массив content помещается в32KiB; при нехватке места они опускаются, исходные text/structuredContent не обрезаются. Это не изменяет прежний отдельный предел structured research JSON и не вводит общий32KiB предел JSON-RPC envelope с дублированным содержимым. Конкретное отображение панели источников зависит от MCP-клиента; платформенные частные metadata не добавляются.
