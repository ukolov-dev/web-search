# Проверка реализуемости ТЗ 1.2 — 28 октября 2026 года

**Результат: первый этап пока не принят.** Минимальное приложение на Rust собирается и выполняет реальные HTML-запросы, извлечение и вызов oMLX. Основные блокеры — отсутствие подтверждённой пары качественных HTML-источников и неподтверждённая полная сетевая защита браузера. Перейти к разработке полного research как будто гипотеза уже подтверждена оснований нет.

Это отчёт об испытаниях конкретной машины и сети, а не общий вывод о невозможности живого поиска или Rust. [ТЗ 1.2](tz-v1.2.md) и его численные пороги не изменены. [Инструкция воспроизведения](../README.md), [сводка JSON](../feasibility/results-2026-10-28.json).

## Сборка Rust-стека

Зафиксированы совместимые версии: Tokio 1.54.1, Axum 0.8.9, reqwest 0.13.5 с rustls, dom_query 0.29.0, dom_smoothie 0.19.0, rusqlite 0.41.0 с bundled SQLite, chromiumoxide 0.9.1, clap 4.6.7, utoipa 6.0.0, tracing 0.1.44. Остальные точные версии находятся в Cargo.lock. SQLite в исполняемой пробе сообщает 3.54.1.

Debug- и release-сборки выполнены; release — Mach-O arm64, около 17,9 МБ без учёта Chromium, модели и кэша зависимостей. Это размер бинарника, а не потребление памяти приложения. Производительность полного сервиса и память исследований не измерялись.

При выборе features выяснилось: chromiumoxide 0.9.1 не имеет `tokio-runtime` feature, а его `rustls` feature включает необязательный fetcher. Пробник использует установленный Chrome, поэтому fetcher и его TLS/ZIP-зависимости исключены. Автоматического скачивания браузера при работе приложения нет.

REST API crates.io возвращал 403. Официальные sparse-индекс и архивы доступны: зависимости получены оттуда без альтернативного неофициального registry. Наличие Axum/utoipa в собранном графе зависимостей не означает реализации production-обработчиков или OpenAPI-контракта.

## Извлечение HTML

До запуска зафиксированы [20 страниц и маркеры](../feasibility/extract-cases.json): Rust Book, SQLite, Python, MDN, Wikipedia RU/EN и Tokio.

- Все 20 страниц получены и обработаны без сетевой или парсерной ошибки.
- На 19 из 20 присутствуют все заранее заданные маркеры основного материала.
- html11, MDN ETag: потерян вводный блок с объяснением и маркером conditional. Локальный повтор по сохранённому HTML показал ту же потерю уже в `article.text_content` библиотеки dom_smoothie, до нашего обхода блоков.
- html07, SQLite FTS5: текст явно ограничен 100000 code points и отмечен truncated.
- Выборочный ручной просмотр начала текстов подтверждает наличие основного материала; заметны повторы/остатки инфобоксов на части Wikipedia-страниц. Полная ручная оценка каждой страницы по критерию ТЗ ещё не завершена.

**Вывод:** dom_smoothie пригоден для дальнейшей проверки, но «19 маркерных проверок» не объявляются 19 полностью принятыми страницами. Нужно отдельно оценить потерю вступлений, дубли вложенных блоков и сохранение нужных фактов в длинных страницах.

## oMLX и модель

Список моделей получен после авторизации. Выполнены два одинаковых коротких запроса: вызвать `search` с аргументом `query = rust ownership`. Приложение проверило имя функции, число вызовов и точное JSON-содержимое аргументов; сам поиск по команде модели автоматически не исполнялся.

| Параметр | Первый вызов | Повторный вызов |
| --- | --- | --- |
| HTTP | 200 | 200 |
| Валидный native tool call | Да | Да |
| Полное время клиента | 25,607 с | 2,048 с |
| Вход / выход | 108 / 40 токенов | 108 / 40 токенов |
| Cached input tokens | 0 | 105 |
| Generation tokens/s по серверу | 40,43 | 42,36 |

Параметры: temperature=0, max_tokens=256. Первый вызов нельзя автоматически называть чистым замером загрузки холодной модели: отдельно загрузка не изолирована. Повтор использует почти полный prefix cache; нельзя экстраполировать 2 секунды на новые длинные исследования.

JSON-fallback не понадобился и не проверялся. Два одинаковых простых вызова подтверждают базовую возможность, но не надёжность многошагового цикла, все форматы инструментов или устойчивость к инъекциям. При лимите 6 генераций и 180 секунд скорость необходимо повторно проверить на реальном контексте.

## Chromium и сетевая защита

Временный профиль Chromium успешно запускается из Rust. Синтетический документ подставлен через CDP Fetch.fulfillRequest; inline-JavaScript изменил заголовок на JS_RENDER_OK. TLS-проверка и sandbox не отключались, пользовательский профиль не использовался.

HTTP-перехват включён до перехода; все запросы, кроме ровно одного синтетического документа, отклоняются. Страница пытается сделать fetch и создать WebSocket к одноразовому локальному приёмнику, не содержащему реальных внутренних данных.

Первый вариант имел loopback origin самой fixture и показал три TCP-соединения к приёмнику. Это могло включать предварительные соединения, связанные с самим origin; считать их доказательством WebSocket-утечки некорректно. Поэтому проведён уточняющий вариант с синтетическим **http://fixture.invalid/**, который вообще не должен разрешаться в адрес локального приёмника.

В уточняющей пробе:

- JavaScript выполнен;
- два HTTP-запроса перехвачены и отклонены;
- одно TCP-соединение всё равно принято локальным приёмником;
- HTTP-строка запроса и полезные данные на нём не получены.

**Вывод:** не доказана передача данных или конкретный WebSocket-обход; зато полного запрета сетевого назначения одним HTTP-перехватом не подтверждено. Требуется контроль на уровне фактических соединений и отдельная проверка всех targets/frames/WebSocket/DNS rebinding. Публичный URL невозможно передать команде browser: пока доступна только фиксированная изолированная fixture.

Пять публичных JS-страниц по критерию 4/5 не прогонялись, поскольку безопасный публичный браузер ещё не квалифицирован. Подменять этот критерий успешным синтетическим рендерингом нельзя.

## Проверки кода и границы результата

В локальных модульных тестах проверяются запрет приватных/специальных IPv4/IPv6 и необычных записей loopback, userinfo и локальных имён, смешанных DNS-ответов; декодирование поисковых редиректов и удаление tracking-параметров; реклама/пустая выдача/CAPTCHA/неизвестная разметка; извлечение основного текста без маркера навигации. Настоящий управляемый DNS-rebinding сервер и полный набор браузерных атак не проверялись.

В HTTP-пробе вручную обрабатываются редиректы, отключены прокси и автоматические повторы, проверенные DNS-адреса закрепляются в клиенте и сравниваются с peer address. Это основание для дальнейших интеграционных тестов, а не заявление о завершённом аудите SSRF.

Результаты обычных тестов, fmt, clippy и release-сборки зафиксированы в машинной сводке. Подробные HTML и тексты лежат только в `runs/2026-10-28/`, исключены из Git; их контрольные суммы — в JSON-сводке. Автоматическая очистка по сроку и лимиту пока не реализована; артефакты требуют ручного контроля, как описано в README.

## Решение и следующий шаг

1. **Rust и локальная модель — предварительно подтверждены.** Оснований возвращать Python из-за сборки нет.
2. **Извлечение — перспективно, приёмка не завершена.** Сохранить кандидат и проверить известную потерю вступления на эталонах.
3. **Пара поисковиков — не подтверждена.** Следующая проверка должна выяснить причину искажённого HTML Bing и найти доступный независимый резерв на исправленном наборе. CAPTCHA/429 не обходить и API не подставлять.
4. **Браузер — только диагностический режим.** До публичного чтения подтвердить реальное ограничение исходящих соединений; одного Fetch-перехвата недостаточно для объявления защиты.

Полный API, кэш и цикл research на этом этапе не реализованы. Второй живой прогон в другой день, 8/10 ответов research, метрики цитирования, p95 полного исследования и весь комплект приёмки остаются непроверенными. Согласно ТЗ, текущие данные оформлены как непройденная проверка гипотезы, а не как принятый пилот.
