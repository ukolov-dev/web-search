# Полная B17 retrieval policy в Rust и свежая проверка — 29.10.2026

Перенесён весь согласованный retrieval-путь B17: фиксированные формы → Seznam/Naver HTML → дедупликация и excerpt → классификация **всех** ID локальной 9B → direct-first и fresh RRF → локальный site-фильтр → top10. Доступен экспериментальный MCP `ranked_search` и CLI для одного вопроса/набора. Это завершение переноса retrieval policy; полный `research` из ТЗ ещё не реализован.

Свежий Rust-прогон исходных 20 вопросов дал **16/20 по собственной предварительной ручной SERP-оценке**. Результат пограничный: без прямой оценки карточки о настройке synchronous в SQLite WAL — **15/20**. Обе цифры приведены для прозрачности; квалификация источников и приёмка пилота не объявляются. Это тот же календарный день, что у исходного B17, и уже известный калибровочный набор. Второго дня и независимого holdout здесь нет.

Машинный отчёт: [full-policy-live-results-2026-10-29.json](../feasibility/full-policy-live-results-2026-10-29.json). Задача Project Context: TASK-20261029-192811-001. Выполнена собственная проверка автором реализации, независимая acceptance-review отсутствует.

## Что перенесено

- [policy.rs](../src/policy.rs): неизменённые original20 и frozen формы B17, раздельная export/classifier-канонизация, выбор самого длинного сниппета, excerpt 300 символов с шагом 150, упорядоченные C-ID, RRF с k=60, classify-all и direct-first. Final site guard действует до top10, даже если модель выбрала чужой домен.
- [model.rs](../src/model.rs): собственный oMLX на loopback; модель `MiMo-V2.6-Distill-Qwen-9B-OptiQ-4bit`, temperature=0, max_tokens=1200, thinking=false, tool_choice=none. Строгая JSON schema; повторные, пропущенные и неизвестные ID, tool calls и незавершённый ответ отклоняются.
- [mcp.rs](../src/mcp.rs): четвёртый инструмент `ranked_search`. Доверенный startup-параметр `--omlx-settings`; MCP-аргументы не могут менять endpoint, ключ или путь к настройкам. Без параметра модель не читается, новый инструмент отвечает model_unconfigured, остальные три работают как прежде. Circuit блокировки общий с обычным search.
- [main.rs](../src/main.rs): явные `ranked-suite` и `ranked-search` с `--live` и новым выходным каталогом, который нельзя перезаписать. В CLI сохраняются сырые HTML, кандидаты и модельные входы/ответы без ключа. MCP не сохраняет capture на диск и не возвращает внутренний pool/протокол модели.

Лимиты на вопрос: ≤4 формы, ≤8 логических SERP, ≤3 классификации, ≤24000 Unicode code points source context на вызов, 180 секунд retrieval/classification. Проверка доступности локальной модели выполняется отдельно, до 15 секунд; клиентский timeout — 210 секунд. При невалидной/неполной классификации сохраняются результаты и ошибки, метки сбрасываются целиком, выдаётся partial RRF. Более 72 кандидатов нельзя молча урезать для модели. Repair/retry не добавлен. Документы целей этим инструментом не читаются.

**Ограничение переноса:** frozen переводы действуют только для точного совпадения с 20 калибровочными вопросами. Любой новый вопрос отправляется двум источникам в исходной формулировке. Общий LLM-rewrite, release-root helper, автоматический failover, factual-answer gate, кэш продукта, публичный Chromium и VPS не включены. RRF объединяет два источника, но не делает их отдельно квалифицированными main/reserve.

## Проверка соответствия B17 до живой серии

Именной offline replay `policy::tests::b17_export_parity` прошёл на всех 20 случаях: raw HTML разобран Rust-парсером, candidate pool совпал целиком, совпали RRF ranks и точные source context/system prompt для модели. Сравнивались сохранённые HTML и входы исходного B17. Старые gold и ответы модели **не были входами новой живой серии**. Replay не выполнял сеть/генерацию и не подтверждает текущее состояние поисковиков.

Исходные файлы B17 и day2 wrapper в соседнем research-проекте не изменялись. Хеш original20: `b67e3269830ae0e976aa9b4c5dc2f6b9c3e922ad1adda35738289d6b1b8325d6`. Forms зафиксированы в [b17-policy.json](../feasibility/b17-policy.json). Настройка по результатам текущей серии не выполнялась.

## Что показали провалы

**Rust/Python HTML (ru07/en07):** лишь одна явно сравнительная карточка fastCRW. Остальное — bindings, каталоги библиотек, общий Rust/Python, PDF extraction или посторонние темы. Classify-all не может создать отсутствующие сравнения; некоторые неполные кандидаты модель всё равно назвала direct.

**Stable Rust October 2026 (ru08/en08):** отсутствуют три карточки, подтверждающие актуальную версию в нужном периоде. releases.rs показывает stable и относительный countdown будущих выпусков, но явная октябрьская дата состояния в сниппете не подтверждена. Другие карточки — старые релизы, общие downloads и проекты с Rust в названии. Репутация домена и память модели не восполняют дату. У ru08 дополнительно parser_changed на исходной русской Naver-выдаче; остальные источники результата сохранены.

**Шум в direct:** среди выбранных карточек встречаются реклама курса/книги, старые docs, пустой/биографический сниппет, copyright и неполные API signatures. Нужны независимая калибровка и проверка по прочитанным страницам. Статус ok здесь означает успешное выполнение пути, а не достаточность ответа.

## Следующие проверки

Сначала независимо разобрать пограничные SERP-оценки и повторить frozen policy в другой календарный день с предварительной проверкой состояния источников. Проверку полноты extract на JCAR/n8n и фактическую поддержку ответа следует закрывать отдельно; новая модельная метка direct эти проблемы не решает. До этих проверок общий поиск, два отдельных поисковых источника и весь пилот не считаются принятыми.
