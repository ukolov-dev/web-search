# Продолжение проверки реализуемости — 28.10.2026

Продолжение [первого отчёта](feasibility-2026-10-28.md). Исходные результаты сохранены без переписывания. **Этап всё ещё не принят:** пары квалифицированных поисковых источников нет, разрешённое публичное браузерное чтение не реализовано.

## Браузер и открытый движок

Для поставки выбран headless Chromium — [открытый браузерный проект](https://www.chromium.org/Home/). Rust-приложение управляет отдельным процессом через chromiumoxide/CDP. Встраивание собственного движка или переход на Servo для текущего пилота не требуются. Испытан установленный Google Chrome; отдельная поставка Chromium и Linux ещё не квалифицированы.

Уточнение про независимость задач: открытость движка не обеспечивает автоматически запрет приватной сети, а его смена не является исправлением сетевой политики.

## Два воспроизведённых дефекта пробы

1. В chromiumoxide::BrowserConfig::arg передавались строки с готовым `--`; библиотека добавляла ещё один префикс. Реальный argv содержал `----disable-component-update`. Исправлены ключи. Регрессионный тест запуска mock executable через настоящий launcher: **exit 101 → 0**.
2. В исходном синтетическом сценарии HTTP-перехват отклонял запросы, но TCP-приёмник получал одно соединение. Сетевой регрессионный тест записан уже после исправления флагов и воспроизвёл это отдельно: **1 вместо 0, exit 101**.

Для второго случая добавлен локальный proxy с запретом всего трафика. В конфигурации браузера удалён implicit loopback bypass, чтобы localhost также проходил через него; это соответствует [описанной Chromium семантике прокси](https://chromium.googlesource.com/chromium/src/+/HEAD/net/docs/proxy.md#overriding-the-implicit-bypass-rules).

После исправления **тот же сетевой тест проходит, exit 0**, повторный прогон также прошёл. Fixture по-прежнему исполняет JS и пытается вызвать fetch/WebSocket к приёмнику; проверка дополнительно требует, чтобы proxy действительно принял соединения. Release-проба показала:

| Наблюдение | Значение |
| --- | --- |
| JavaScript выполнен | Да |
| Отклонённые запросы HTTP | 2 |
| TCP-соединения к приватному приёмнику | 0 |
| Соединения, отклонённые диагностическим proxy | 16 |
| Публичное браузерное чтение включено | Нет |
| Полная SSRF-защита и DNS rebinding квалифицированы | Нет |

**Граница исправления:** proxy пока запрещает весь трафик. Это доказанный проход контролируемого диагностического сценария, а не готовая схема чтения публичного веба. Нужны разрешающий только проверенные публичные назначения шлюз, проверка DNS rebinding, новых targets/frames, WebRTC, workers и загрузок. Итоговая защита по ТЗ пока не принята. Передача полезных данных через старое пустое TCP-соединение не доказана; его точный инициатор не установлен.

Дополнительные эксперименты с macOS sandbox-exec — полный запрет network-outbound и запрет исходящих IP-соединений с сохранением прочих операций — завершились таймаутами браузерной пробы. Их нельзя считать доказательством изоляции или готовым способом запуска. Настройки ОС и пользовательского Chrome не менялись.

Подробные захваты команд и red/green — в [отчёте Bug Reproducer](../outputs/bug-reproducer-report.md). Фоновые сервисные задачи пробы теперь управляются JoinSet, который отменяет их при завершении/ошибке; путь браузера опционален и может определяться штатно вместо фиксированного пути macOS.

## Два режима размещения

В [ТЗ 1.3](tz-v1.3.md) закреплены:

- **local:** текущая работа на Mac, CLI и loopback API, локальный oMLX;
- **server:** тот же прикладной код и HTTP-контракт на собственном Linux VPS, отдельный будущий этап.

Параметры запуска и доверенного LLM endpoint должны задаваться конфигурацией. oMLX не предполагается установленным на обычном Linux VPS: модель может оставаться на собственном Mac/вычислительном узле с защищённым подключением либо впоследствии использовать другой собственный совместимый backend. Сторонние LLM API не разрешаются этим изменением.

Фиктивный переключатель режимов, Linux-деплой и публичный API сейчас не добавлены. VPS не выбирался и не изменялся. Перед удалённым предоставлением API отдельно проверяются Linux-сборка, аутентификация, защищённая точка входа и качество поиска из сети сервера.
