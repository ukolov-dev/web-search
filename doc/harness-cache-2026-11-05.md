# Harness NEW20: кэш, качество, задержка и стоимость

Дата: **5 ноября 2026**. Кэш реализован как opt-in. На 18 задачах, завершившихся во всех основных режимах, медиана полного ответа Harness снизилась **35,64 → 25,43 с (−28,6%)**; относительно новой версии с пустым кэшем — **32,22 → 25,43 с (−21,1%)**. Внутри `ranked_search` HTTP-обращения сократились **85 → 37**, вызовы Qwen — **41 → 1**. Стоимость API на тех же 18 задачах выросла **$0,019083 → $0,021019 (+10,1%)**. Экономия генеративных вызовов не подтверждена.

Качество конечных ответов и `direct` остаётся ограничением. В основной серии: **20/20 → 18/20 → 19/20** завершённых эпизодов; три сбоя соединения позже восстановлены отдельными парами. FP direct **1 → 1 → 1**, но холодный проход создал **другой FP ID**. В прогретом ответе появилась новая неверная рекомендация про `Sequence[int]`. Кэш остаётся явно включаемым экспериментом; общий quality gate не закрыт.

## Что запускали

Использован настоящий **DeepSeek Harness SDK**, npm `@deepseek-ai/dsh@0.2.2-rc.1`, соответствующий установленному Desktop-релизу; отдельный Node **v24.22.2**. `initialize` подтвердил `deepseek-harness-sdk-runtime`, события содержат реальные native MCP calls и ответы. Драйвер управляет RPC SDK; цикл работы с моделью выполняет Harness. Основные сведения об интерфейсе: [официальный Harness](https://github.com/deepseek-ai/deepseek-harness). Рабочий профиль Desktop не менялся.

Фиксированные настройки: `deepseek/deepseek-v4.1-flash-1017` через уже разрешённый OpenRouter; local `Qwen3-Reranker-0.6B-4bit`; `--evidence-memory`, прежние selector/retrieval/literal/date/coverage/audit gates. Модель вызывается заново в каждом эпизоде. Каждый эпизод — новый Harness home, разговор, workspace и MCP-процесс. Агент видит только `search/ranked_search/discover/extract`; максимум 4 вызова инструментов и 6 внешних генераций Harness, до 360 секунд. Внутри ranked сохраняются прежние 3 генерации, 4 document reads, 4 Qwen и 180 секунд. Межвызовный product-бюджет этим не квалифицирован.

[NEW20](../feasibility/harness-cache-cases-2026-11-05.json) заморожен до основной серии: 10 RU/10 EN поисковых запросов; 4 новости, 8 документационных, 4 сравнения, 4 ложные предпосылки. Голд и reference URL агенту не передавались. Исходные original20 и B17 не изменены, их SHA-256 сверены. Из-за русской служебной инструкции ответы преимущественно русские; это не проверка англоязычного ответа в обычном Desktop-профиле.

Три основных условия: исходная версия без кэша; новая версия с отдельной пустой SQLite-базой для каждой задачи; немедленный повтор с той же базой после перезапуска MCP. Пустой кэш может дать hit внутри одного эпизода после первого чтения. Прогрев локальной модели и персистентность кэша — разные условия; Qwen был доступен до baseline.

До основной серии исправлены несовместимый старый `tools.mode` в SDK-адаптере и повторная инициализация пустого capture-каталога. Первый живой H01 агент провёл с Bing/DDG; он сохранён как отдельная development-попытка. Основной протокол затем ограничен Seznam/Naver без изменения задач/голда. Все 20 baseline/cold/warm используют этот одинаковый протокол. Baseline отличается от исходного бинарника только наблюдаемостью и сохранением source refusals, без кэша и настройки релевантности; обе версии исходников и хэши сохранены.

Naver на baseline H06 вернул verification page и был отключён до конца эксперимента. Отказы TfL, Hermes и London Transport Museum также сохранялись между процессами. Новых прокси, поисковых API и обхода challenge не было. Изменение доступности источников ограничивает причинное сравнение baseline с более поздними сериями.

## Измерения

В таблице ниже — **те же 18 завершённых задач** H01–H18. H19/H20 не исключены из общей статистики: их исходные сбои показаны отдельно ниже. Использовать быстрый обрыв как ускоренный готовый ответ было бы неверно.

| --- | ---: | ---: | ---: |
| Медиана полного ответа, с | 35,64 | 32,22 | 25,43 |
| p95, с, nearest rank | 186,16 | 71,33 | 56,40 |
| Generative calls: Harness + поиск | 55 + 37 | 55 + 39 | 55 + 38 |

Задержка — от `session/prompt` до `turn/end`, включая вызовы MCP и финальную генерацию, без startup. Startup отдельно есть в JSON. p95 при n=18 близок к максимуму; длинный baseline H15 включает сетевые ожидания, поэтому сокращение хвоста нельзя целиком приписать кэшу.

**Точные счётчики внутри ranked_search**, на тех же 18 задачах:

| Операция | Пустой | Прогретый | Изменение |
| --- | ---: | ---: | ---: |
| HTTP send, включая ошибки/redirect hops | 85 | 37 | −56,5% |
| Local Qwen attempts | 41 | 1 | −97,6% |
| Запуски извлекателя | 53 | 13 | −75,5% |
| Ошибки операций кэша | 0 | 0 | 0 |

Для исходного бинарника полного HTTP-счётчика нет. Дополнительные `extract/search/discover` считаются по исходным успешным capture-файлам; неудачные дополнительные пробы дают только нижнюю границу общего HTTP-счётчика эпизода. Они не добавлены к таблице точного ranked-счётчика. Предварительный разбор клиентского текста недосчитывал большие ответы; итог пересчитан по полным capture JSON.

Стоимость взята из provider `usage.cost`, отдельно от локального compute; энергия, RAM и время oMLX не оценивались. В 18 полных парах неизвестных стоимостей нет. Между cold/warm сумма уменьшилась на 5,7%, но относительно baseline выросла на 10,1%. Число генераций почти не изменилось; менялись решения модели, объём контекста и ответы. Кроме того, provider prompt-cache сработал независимо от нашего кэша: 208896 → 219648 → 250880 cached input tokens. Считать разницу цен доказанной экономией именно нашего кэша нельзя.

## Качество и сбои на всех 20 задачах

Разметка — собственная ручная, с проверкой сохранённых страниц и ответов; независимой приёмкой не является. 48 фиксированных технических аспектов в 16 задачах: C — корректен и поддерживается снятым reader-корпусом/обоснованным выводом; U — корректен/правдоподобен, но источника недостаточно; W — неверен; M — отсутствует. C не гарантирует, что нужный фрагмент пережил ограничение контекста Harness. Для новостей отдельно оценивается выполнение запроса, без предположения, что восемь подходящих статей обязательно существовали.

| Основные 20 эпизодов | Без кэша | Пустой | Прогретый |
| --- | ---: | ---: | ---: |
| Завершён финальный ответ | 20/20 | 18/20 | 19/20 |
| Корректные аспекты C+U / 48 | 47 (97,9%) | 42 (87,5%) | 44 (91,7%) |
| C / U / W / M | 46 / 1 / 1 / 0 | 41 / 1 / 0 / 6 | 43 / 1 / 1 / 3 |
| Достоверные direct / FP / unknown | 12 / 1 / 2 | 8 / 1 / 1 | 12 / 1 / 2 |
| Технические задачи с ≥1 достоверным direct | 8/16 | 5/16 | 8/16 |
| Готовые новостные подборки из двух статей | 0/4 | 0/4 | 0/4 |
| Честный отказ при нехватке новостных статей | 4/4 | 4/4 | 4/4 |
| Ссылки на URL с успешным reader-чтением | 33/33 | 31/35 | 33/38 |

Покрытие direct на задачах не равно документному direct recall или recall всего веба. Для последнего нет полного независимо размеченного множества подходящих страниц. `unknown` не засчитаны в верные direct. Прочитанный URL также не доказывает правильность цитаты или поддержку каждого вывода.

Конкретные проблемы:

- Baseline и warm: H06 ошибочно повышают [CPython issue #140947](https://github.com/python/cpython/issues/140947) — воспроизведение конкретной утечки контекста вместо общего ответа о копировании Task/thread context.
- Cold: этот FP исчез, но появился **новый** H07 [Dumbarr/Dockge](https://dumbarr.com/deployment/dockge/): практическая конфигурация без объяснения рекурсивности и обоих направлений propagation. При строгой разметке это background. Одинаковое число FP 1→1 не означает отсутствие новых FP.
- H09: два baseline/warm direct не имеют target body в соответствующем эпизоде (Marek Honzal и schpet). Cold прочитал schpet, поэтому там unknown один. Исторический body не подменяется страницей из другого прохода.
- H05: baseline/warm неверно объясняют повторное чтение Tokio watch без нового send; cold правильно описал гонку с новым значением между `changed` и `borrow`. [Документация Tokio](https://docs.rs/tokio/latest/tokio/sync/watch/) требует именно это условие.
- H13 warm: к правильному ответу о `Final` добавлено неверное предложение использовать `Sequence[int]` для настоящей неизменяемости. Аннотация не замораживает объект во время выполнения. [Python typing](https://docs.python.org/3/library/typing.html).
- H18 baseline/warm: таблица считает любой сигнал failure для systemd, теряя clean-signal exceptions; cold привёл цитату об исключениях. [systemd.service](https://www.freedesktop.org/software/systemd/man/latest/systemd.service.html).
- H10: `rerere.autoupdate` объяснён по памяти/догадке, в прочитанном тексте опции нет. H11 цитирует раздел RFC9110, который reader обрезал до него, хотя пригодное ETag-доказательство было в другом прочитанном RFC7232. Это разрыв между правильным знанием, доступным доказательством и атрибуцией.

На 19 cold/warm парах, где оба раза состоялся ranked: SERP hashes совпали **19/19**, первые внутренние LLM inputs — **19/19**, но ответы начального классификатора различались **9/19**. В 53 общих чтениях совпали все text hashes; 43 взятых из кэша Qwen responses совпали с cold как JSON-значения. Изменение `direct` при одинаковом входе модели нельзя считать изменением текста из-за кэша. При этом наблюдённые регрессии не скрыты и не дают оснований объявить качество стабильным.

Важное ограничение Harness-профиля: **5 / 4 / 5** больших MCP-результатов в основных сериях попали в spill. Например, H11 `extract` сохранил полное форматированное представление в локальный файл и сообщил об исключённых **109083 bytes**. Агенту остались начало/конец, а native `read` в этом четырёхинструментном профиле недоступен. Обычный Desktop с разрешённым чтением spill-файла может вести себя иначе. Это ограничивает интерпретацию source grounding и объясняет часть неполноты независимо от Rust-extractor. На текущем тесте нельзя заявить 100% сохранность доказательств в фактическом контексте Harness.

Три первичных сбоя: H19 cold — до вызова MCP, H19 warm — после ranked, H20 cold — без финального ответа. Во всех случаях Harness завершился `TRANSPORT / Connection error`; relay записал `URLError`. Содержимое HTTP 403/429 от OpenRouter не получено. По основным 60 попыткам известная стоимость:

| Серия | Известно, USD | Generative attempts без usage.cost |
| --- | ---: | ---: |
| Baseline | $0,022799 | 0 |
| Cold | ≥$0,022415 | 3 |
| Warm | ≥$0,024843 | 1 |

Четыре неизвестные стоимости не приравнены к нулю. После отдельной успешной проверки соединения H19/H20 выполнены по **одной восстановительной cold/warm паре** на новых базах: 4/4 завершены, все 6 технических аспектов в каждой recovery-серии корректны. Восстановление обошлось в известные **$0,009830**; оно не заменяет провалы основной серии. Две служебные оплаченные пробы перед основной серией — ещё **$0,000773**. Их ответы, расходы и исключение из основных метрик сохранены.

## Реализация и проверка

Кэш: [cache.rs](../src/cache.rs), [HTTP](../src/net.rs), [Qwen](../src/model.rs); включение и очистка — [MCP-контракт](local-mcp.md#локальный-кэш--5-ноября-2026). По умолчанию кэш отключён. SQLite WAL/FULL, хэши, TTL/validators, отдельные query/version keys, cleanup/eviction, один владелец базы. Модельные ответы и verdicts не кэшируются. Полный HTML разрешён только явным startup по этому запросу пользователя; credentials/cookies не сохраняются.

После измерений дополнительно ограничен TTL распознанных feed при standalone discover/extract и чтении старых широких TTL-записей, а `source_cache.expires_at` исправлен до фактически применённого ограничения. Консервативный Feed-detector может сократить TTL главных/поисковых страниц. Это отдельное исправление guard/диагностики, не настройка quality по NEW20. Измеренный бинарник и исходники сохранены отдельно от финальной сборки. Все 60 эпизодов после этой небольшой правки не повторялись; её доказывают отдельные offline regression и свежая MCP-проба, а не прежний benchmark.

Финальные проверки: **124 unit + 6 stdio = 130 ordinary tests**, fmt, clippy all-targets `-D warnings`, release build и 6 fresh release-stdio прошли. Проверены TTL boundary/clock rollback/restart, digest corruption, eviction/cleanup, single owner, запрет private URL, source-state и cached redirect к отключённому хосту до DNS. Fresh release MCP: warm text hash неизменен, 0 HTTP/0 extraction; refresh сделал 1 HTTP и сохранил fetched_at при 304. Обычный `--ignored` целиком не запускался. Пиковое суммарное место SQLite/WAL/temp и Linux/VPS/multiworker не измерялись.

Контекстный refactor-review без Git вернул пустой diff scope; это не semantic review. Реальные изменения сверены по сохранённым before/after sources и unified diff. Независимая acceptance-review отсутствует; результат формального Task Contract сохранён как partial: quality-gate и независимая acceptance не закрыты, реализация и запрошенный эксперимент выполнены.

Offline-пересчёт без сети/моделей из корня проекта:

```sh
mkdir runs/harness-cache-replay-20261105
tar -xzf feasibility/harness-cache-corpus-2026-11-05.tar.gz -C runs/harness-cache-replay-20261105
python3 scripts/analyze-harness-cache.py --run-root runs/harness-cache-replay-20261105 --quality-file runs/harness-cache-replay-20261105/evaluation/quality.json --output runs/harness-cache-replay-20261105/recount.json
```

Долговечный пакет ограничен 64 МиБ compressed / 256 МиБ inputs и не зависит от очистки обычного runtime-кэша. Его срок — до отдельного решения заменить или удалить экспериментальные доказательства; `cache-clear` архив не трогает. Новый живой прогон требует новой серии/каталогов, проверки source refusals и актуального календарного окна; исторические news-запросы нельзя выдавать за свежие сегодняшние.

Следующий приоритет — согласовать размер MCP-ответа и доступ к spill в реальном Harness-профиле, затем проверять конечные утверждения по видимым фрагментам. Отдельно нужны более устойчивые доступные retrieval-источники и контроль неопределённого model transport. Этот эксперимент даёт работающий opt-in cache и измерения, но не общую квалификацию поиска или перенос автоматически на Desktop/VPS.
