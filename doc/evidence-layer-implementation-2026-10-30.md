# Слой проверки и короткая память evidence: реализация и A/B — 30.10.2026

**Реализован экспериментальный режим `--evidence-memory`. По умолчанию сохранён прежний legacy: улучшение качества новым слоем не подтверждено.**

На 12 новых вопросах / 201 карточке после чтения страниц baseline получил TP5/FP0/FN13, новый v2 — TP4/FP0/FN14: **recall 27,8% → 22,2%, ложные direct 0 → 0**. На восьми вопросах с валидной общей исходной классификацией — 38,5% → 30,8%. Это сравнение текущих pipeline на одном DeepSeek, а не доказательство пользы памяти.

Запись задачи: TASK-20261030-135808-001. Авторские проверки и разметка; независимая приёмка не проводилась.

## Что внедрено

- [evidence.rs](../src/evidence.rs): ограниченное состояние одного запроса, единый путь проверки исходных SERP-direct и потенциальных body-promotions; неподтверждённые direct становятся background.
- Исходный вопрос остаётся целиком как R0. Модель выделяет до трёх дополнительных точных уникальных подстрок вопроса; приложение привязывает их к UTF-8 диапазонам. На втором шаге условия менять нельзя. Это неполная декомпозиция: часть условий остаётся только в общем R0.
- Для каждого условия сохраняются supported/missing/contradicted/ambiguous и ID реальных фрагментов того же кандидата. Поддержка требует существующих фрагментов; слово supported без ссылок, title-only core, чужие/дублированные ID и выдуманные anchors отклоняются.
- При пробелах выбираются до четырёх страниц. Из уже извлечённого текста выбирается до трёх фрагментов с учётом вопроса и незакрытых anchors, без повторной загрузки той же страницы внутри запроса. Проверяются exact source ranges, hashes и literal constraints.
- Максимум десять direct/background кандидатов, три модельных вызова включая исходную классификацию, четыре попытки чтения и 180 секунд общего этапа. Модельные inputs ограничены 24000 символами. Непроверенные direct за пределами лимита также понижаются.
- Память существует в Rust-структурах в течение запроса. БД, vector store, прошлые ответы и межпользовательская память не добавлялись. Public MCP-диагностика содержит coverage, пробелы и source references без дублирования всего текста passages; доказательства возвращённых direct доступны отдельно.
- Публичные URL, DNS/IP, редиректы, site-фильтр и блокировки сохранены. [Общий reader](../src/rescue.rs) используется обоими режимами. Browser/VPS/API-сервер и глобальные настройки не менялись.

Формально валидные ссылки не доказывают правильность семантической оценки модели или истинность источника. Direct означает помощь по вопросу, а не полную достаточность ответа. Общий research/answer gate этим изменением не появился.

## Результаты

| Срез / этап | Baseline TP / FP / FN | Новый v2 TP / FP / FN | Recall baseline → v2 |
| --- | ---: | ---: | ---: |
| Все12: SERP + guards / coverage | 1 / 0 / 11 | 1 / 0 / 11 | 8,3% → 8,3% |
| Все12: итог с body | 5 / 0 / 13 | 4 / 0 / 14 | 27,8% → 22,2% |
| Валидные8: итог с body | 5 / 0 / 8 | 4 / 0 / 9 | 38,5% → 30,8% |
| Все12: строгая sensitivity | 5 / 0 / 6 | 4 / 0 / 7 | 45,5% → 36,4% |

В final body-aware gold 18 положительных карточек; в SERP-only gold — 12. Семь заранее отмеченных пограничных положительных карточек понижаются в sensitivity; направление результата сохраняется. Наблюдаемая precision 5/5 и 4/4 не является квалификацией точности. Исходный baseline уже имел FP0, поэтому на этом наборе нечего уменьшать по FP.

95% query-bootstrap интервал разницы body recall нового режима относительно baseline: **−21,1…+25,0 п.п.** для всех12, **−37,5…+50,0 п.п.** для валидных8. Малый набор и авторский gold не позволяют обобщить результат. Нулевой FP в каждом bootstrap-повторе при исходном FP0 не доказывает безопасность на других вопросах.

Из известных пригодных источников в top10 остаются 17/18 у обоих вариантов. Снижение относится к direct-меткам, а не к потере URL из top10. SERP-stage ranking отдельно не измерялся.

## Что произошло с ошибками

- **Общий начальный classifier отказал на n01/n06/n08/n09**: лимит 2400 токенов исчерпан до корректного вывода. Оба варианта используют одни и те же сохранённые initial calls. В all12 эти вопросы дают нулевой direct recall; отдельно показан парный срез valid8. Эту проблему исходной модели слой памяти не исправляет.
- **n05/C001 Docker Compose:** новый v2 нашёл пригодную документацию о depends_on/service_healthy и порядке запуска. Baseline её не повысил. Это один новый TP.
- **n10/C004 JavaScript:** полезный фрагмент про ES2023/toSorted прошёл semantic coverage, но literal gate не нашёл JavaScript именно среди процитированных passages. Слово находится в контексте страницы. Это потерянный TP и избыточно строгий способ связывания literal context.
- **n12/C003 curl:** полная извлечённая страница объясняет --resolve/--connect-to и Host/SNI, но выбранные фрагменты не закрыли R3 “TLS SNI”. Это второй потерянный TP: память фиксирует пробел, однако текущий selector не гарантирует выбор нужного текста.
- **n02 Rust:** оба варианта сохранили C008; часть других пригодных источников осталась background из-за непокрытого self-reference условия в переданных фрагментах.

В сумме +1 TP и −2 TP дают 5 → 4. Два следующих приоритета для отдельного development-эксперимента: учитывать явно предоставленный title/header как context для literal gate и выбирать passages по незакрытому условию с сохранением уникальной полезной части при дедупликации. Эти правки по текущим quality-ответам не внедрялись.

## Технические итерации сохранены

1. Первый reviewer с provider default high исчерпывал 3600 токенов на reasoning: 7 length из9 вызовов. Проверенный каталог модели указывает default high и поддержку low/none.
2. В low осталось 6 length из11. Эти оплаченные ответы не скрыты и не считаются успешной классификацией.
3. Для reviewer закреплённого DeepSeek включён поддерживаемый none; исходный classifier не изменён. В первой версии без reasoning все14 ответов завершились stop, но приложение отклонило четыре пакета из-за non-support references. Итог v1 был TP3/FP0, recall16,7% против27,8% baseline.
4. На сохранённом контрпримере воспроизведён лишний отказ: missing/ambiguous со ссылкой на существующий fragment не означает поддержку, однако раньше отвергал весь пакет. Red→green тест проверяет, что такая строка остаётся background, соседняя supported-строка не теряется, а выдуманный passage по-прежнему отклоняется. V2 допускает проверенные ссылки для этих отрицательных состояний; положительная проверка и all-ID gate сохранены. Все16 новых вызовов завершились stop, новых contract errors в v2 нет.

V2 — **development-повтор после разбора v1**, не новый независимый holdout. SERP-gold не менялся с первого прогона; body-gold зафиксирован до первого quality-анализа и также не менялся. Все технические серии сохранены. Обоснование reasoning-настроек: [официальная документация OpenRouter](https://github.com/OpenRouterTeam/docs/blob/main/guides/best-practices/reasoning-tokens.mdx); actual metadata — runs/evidence-layer-2026-10-30/reasoning-metadata.json.

## Протокол и ограничения

- Frozen replay учитывает shared initial время, но не историческую retrieval-задержку; фактические cases укладываются в180с и с добавлением сохранённого source elapsed. Это ограничение wall-clock сравнения, не расширение runtime-бюджета.

- Вопросы [new12](../feasibility/evidence-layer-cases-v1.json) заданы до изменения поведения и просмотра предсказаний. Original20/frozen B17 forms не менялись. Для новых вопросов используются только исходные формулировки.
- Baseline выполнен старым неизменённым runtime: 24 логических поисковых попытки Seznam/Naver, 31 попытка чтения страниц, 23 генерации. Все source responses200; один Naver parser_changed. Это новый набор вопросов, не day2 квалификация original20.
- Новые варианты используют точно тот же candidate pool и исходные classifier responses. Initial calls не генерировались повторно для улучшения цифр. Для общего URL используются одинаковые сохранённые bytes; документы-кэши служат только benchmark tooling.
- V2: 26 логических попыток чтения, из них20 из source cache и6 свежих fetch attempts. Новых успешно извлечённых документов сверх baseline20 не появилось. Блокировки curl.se, redis.io, stackoverflow.com, superuser.com и npmjs сохранялись; повторов для их обхода не делалось.
- Gold состоит из авторских оценок всех201 карточек. SERP и mixed SERP/body gold показаны отдельно. Fetched documents изначально выбирал baseline; это selection bias и не независимая полнота поиска. Unjudged не считаются FP. Увеличение context/cache само по себе не признаётся доказательством поддержки факта.
- Это pipeline A/B: поменялись prompts/schema reviewer, обработка evidence и его reasoning-mode. Он не изолирует причинный эффект самого хранения памяти. Тест проведён на DeepSeek snapshot1017; все модельные запросы обслужил Morph. Цифры прежнего46-набора с другим provider/данными не сопоставляются как один эксперимент.
- Новая local MiMo вживую не прогонялась; RAM/KV и длительная прогретая сессия не измерялись. VPS, browser rendering, нагрузка, свежий holdout после v2 и независимая приёмка не проверены.

## Запуск

Legacy остаётся default. Для включения нового слоя добавить startup-флаг к текущему разрешённому запуску:

```sh
./target/release/web-search mcp \
  --openrouter-key-file "$HOME/.config/web-search/openrouter.key" \
  --model deepseek/deepseek-v4.1-flash-1017 \
  --openrouter-proxy "$OPENROUTER_PROXY" \
  --evidence-memory
```

OPENROUTER_PROXY должен обозначать уже согласованный локальный маршрут, без автоматической смены после отказа. Флаг также доступен ranked-search/ranked-suite; аргументы MCP-инструмента его не принимают. oMLX transport сохранён, но новый слой на MiMo пока не квалифицирован.

Offline пересчёт без ключей/сети:

```sh
CARGO_HOME="$PWD/.cache/cargo" cargo test --locked --offline benchmark::evidence_layer_first_round_replay -- --ignored --exact
python3 scripts/analyze-evidence-layer-2026-10-30.py
```

Вывод: память сделала причины отказа наблюдаемыми и обеспечивает общий формальный gate, но пока не улучшила recall. Для default-включения нужен следующий фикс на отдельном development-наборе и новый frozen holdout, а не подстройка отчётного gold.
