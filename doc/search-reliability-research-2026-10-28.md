# Интернет-исследование: надёжность поиска для агентов

Дата проверки: **28.10.2026**. Материал дополняет [отчёт реализации](search-reliability-2026-10-28.md) и [пять новых научных работ](search-reliability-papers-2026-10-28.md). Это рекомендации и результаты диагностики; действующее ТЗ v1.3 и производственные параметры поиска не изменены.

## Вывод для нашего проекта

Главное ограничение сейчас — обнаружение подходящих страниц. Предыдущие локальные результаты Bing 9/20 и Mwmbl 2/20 не квалифицируют два источника; у Mwmbl дополнительно смешаны версии бинарника. Rust, MCP и открытый браузер сами по себе не исправят качество внешнего индекса. Нужны отдельные проверки релевантности, полноты доказательств и поведения при отказе.

Найден точный аналог симптома Bing и свежий исправляющий PR. Мы проверили минимальную гипотезу о языке запроса: **на двух отдельных диагностических запросах улучшения релевантности не получили**. Поэтому не включаем параметр в основной адаптер и не расходуем полный приёмочный набор на этот вариант.

## 1. Bing: совпадение симптома есть, готовое решение не подтверждено

В [issue SearXNG #4964](https://github.com/searxng/searxng/issues/4964) описаны нерелевантные ответы Bing, включая обработку только первого слова. [PR #6671](https://github.com/searxng/searxng/pull/6671), объединённый **11 сентября 2026**, меняет параметры локали. Это первичные отчёты разработчиков, а не установленная причина нашего сбоя.

В [текущем Bing Web адаптере](https://raw.githubusercontent.com/searxng/searxng/master/searx/engines/bing.py) используются `q`, настройка safe-search и `setlang`; `cc` не передаётся для `us`, `cn`, `ru`. Функция с `mkt` остаётся для совместного использования другими адаптерами, но текущий Web request её не вызывает. Нельзя делать вывод по одному наличию `mkt` в файле. Более ранняя наша проба с `mkt=en-US/setlang=en/cc=US` не проверяла тот же вариант.

**Наш эксперимент:** по одному `q_only` и `q_and_setlang` для двух новых RU/EN запросов, всего четыре обычных HTML-запроса. Без `cc/mkt`, смены IP, имитации браузерного отпечатка, повторов и обхода ограничений. Запросы зафиксированы в [отдельном fixture](../feasibility/locale-research-cases.json), исходный набор из 20 случаев не менялся. Сохранялась исходная выдача **до site-фильтра**, чтобы видеть поведение источника.

| Запрос | Только q | q + setlang | Ручная оценка по SERP |
| --- | --- | --- | --- |
| `Python asyncio TaskGroup exception handling documentation` | 10 ссылок | 10 ссылок | Порядок URL полностью совпал; общие страницы Python и документации, без прямого материала про TaskGroup. Прямо релевантных кандидатов по шкале 2: 0 в обоих вариантах |
| `site:sqlite.org PRAGMA foreign_keys внешние ключи` | 10 ссылок на 123recht.de | 0 ссылок | Изначально чужой домен и тема; затем явное сообщение Bing об отсутствии результатов. Прямо релевантных кандидатов: 0 в обоих вариантах |

Все четыре ответа — HTTP 200. В RU-варианте с языком прочитан явный HTML-маркер отсутствия результатов: это не потеря десяти ссылок парсером. EN-изменение коснулось языка временных подписей, но не порядка URL. Содержимое найденных страниц в этой пробе не проверялось; совпадение домена документации само по себе не давало оценку 2.

**Интерпретация:** минимальный вариант `setlang` не помог здесь и сейчас. Это не полное воспроизведение SearXNG и не доказательство бесполезности всех настроек локали; также не доказаны намеренная подмена выдачи, виновность IP или TLS. Для очередной серии запросов нужна новая конкретная гипотеза, а не перебор стран и заголовков.

Порядок был фиксированным: сначала baseline, затем кандидат. Временные изменения и влияние порядка не контролировались; выборка слишком мала для статистического вывода.

Артефакты: [четыре ответа и URL переходов](../runs/research-locale-2026-10-28/results.json), HTML рядом с JSON; [долговечная оценка с хешами](../feasibility/locale-research-evaluation-2026-10-28.json). `runs` исключён из Git, сводная оценка — нет. Проба реализована отдельным ignored Rust-тестом `tests::live_bing_locale_research`; существующий каталог защищает от случайного повторного запуска этой серии.

## 2. SearXNG: полезный образец адаптеров, дополнительная зависимость

[SearXNG](https://docs.searxng.org/user/about.html) — метапоиск. Собственная установка собирает ответы внешних источников; наличие сервиса на VPS не гарантирует их доступность или релевантность. Полезно изучать его распознавание выдачи, адаптеры и журнал регрессий.

Проверка исходников выявила важную границу нашего ТЗ:

- [Bing](https://raw.githubusercontent.com/searxng/searxng/master/searx/engines/bing.py) читает HTML без официального API и ключа.
- [Mwmbl](https://raw.githubusercontent.com/searxng/searxng/master/searx/engines/mwmbl.py) в SearXNG использует **внешний JSON API**, хотя ключ не нужен.
- [Marginalia](https://raw.githubusercontent.com/searxng/searxng/master/searx/engines/marginalia.py) использует JSON API с ключом.

**Наша рекомендация:** если сравнивать SearXNG локально, сначала составить разрешённый список именно HTML-адаптеров и зафиксировать конфигурацию/версию. Не подключать стандартный набор источников вслепую. Это отдельный сравнительный эксперимент, не обязательный сервис для Rust/MCP и не основание менять ограничение ТЗ на сторонние поисковые API.

## 3. Что дают альтернативные движки

| Кандидат и первичный источник | Что действительно получаем | Решение для пилота |
| --- | --- | --- |
| [Stract](https://github.com/StractOrg/stract) | Rust-поисковик со своим обходом и индексом; репозиторий архивирован владельцем 02.04.2026 | Читать архитектуру; не брать как активно поддерживаемый готовый резерв |
| [YaCy](https://yacy.net/faq/) | Собственный обход, специализированные индексы и P2P-поиск | Возможен отдельный предметный индекс; покрытие общего веба требует самостоятельной проверки |
| [Marginalia](https://github.com/MarginaliaSearch/MarginaliaSearch) | Собственный индекс с фокусом на текстовый «малый веб»; развёртывание полного поиска требует существенных ресурсов | Не считать заменой общего RU/EN-поиска на небольшом VPS; локально не устанавливался |
| [Tantivy](https://github.com/quickwit-oss/tantivy) | Rust-библиотека полнотекстового индекса | Может ранжировать уже полученный корпус; сама не обнаруживает неизвестные страницы |
| [Lightpanda](https://lightpanda.io/docs/core-concepts/architecture-overview) | Headless-движок с JS/DOM, без графического рендеринга, с CDP | Кандидат для отдельной будущей пробы чтения JS-страниц. Качество поиска и нашу SSRF-изоляцию не доказывает |

Сравнение основано на документации и исходниках, без установки и собственных замеров. Переносить рекламные показатели скорости на нашу машину нельзя. Новые браузеры сейчас не снимают блокер поиска URL; действующий выбор Chromium автоматически не меняем.

## 4. Следующие эксперименты — наши предложения

### P0. Отделить найденную ссылку от достаточного доказательства

На сохранённых результатах разметить три уровня: кандидат относится к вопросу; извлечённый текст содержит нужные сведения; утверждения ответа подтверждены фрагментами. Сохранять причины отказа и пропущенные части вопроса. Сначала ручная контрольная разметка, затем сравнение с локальной 9B-моделью. Самооценка модели без калибровки не становится вероятностью истинности. Основания: R23, R24, R27 в [каталоге](search-reliability-papers-2026-10-28.md).

### P1. Один ограниченный повторный поиск с переформулировкой

Проверить отдельно на новом development-наборе: исходный запрос против исходного плюс **одна** более точная формулировка. Сохранять сущности, даты, обязательный `site:` и исходный смысл; записывать обе строки. CAPTCHA/403/429/challenge прекращают источник, переформулировка после блокировки не выполняется. Мерить прирост релевантных страниц, потерю ограничений, число запросов и время. Это предложение на основе R25; обучение rewriter и обещание опубликованного эффекта не требуются.

Негативная locale-проба не даёт основания сейчас запускать полный набор ещё раз. Выбор варианта фиксируется после development-проверки; исходные 20 случаев используются для отдельного последующего сравнения без замены неудачных запросов. Они уже просмотрены ранее, поэтому это регрессионная оценка, а не слепой holdout. Для проверки переноса нужен новый, заранее зафиксированный набор. Приёмка ТЗ остаётся минимум 16/20 в каждом из двух прогонов в разные дни и требует двух пригодных источников.

### P2. Живой переход по ссылкам официальной документации

**Собственная гипотеза:** если агент уже знает доверенный официальный корень или пользователь указал сайт, прочитать HTML-навигацию и выбрать реальные внутренние `href` по теме, затем прочитать 2–3 страницы в пределах общего лимита восемь URL. Каждый URL/редирект проходит действующую сетевую проверку. Без угадывания глубоких адресов, массового предварительного обхода и внешнего API. При отсутствии корня этот путь нельзя представить как универсальное обнаружение сайта.

Диагностика SQLite с переданными URL ранее показала работоспособность чтения и ответа, но не обнаружения ссылок. Поэтому новый сценарий оценивать отдельно: найден ли нужный внутренний URL, поддержан ли ответ, сколько загрузок понадобилось. Это может помочь агентским вопросам по документации, но само по себе не закрывает общий поиск и требование трёх релевантных ссылок. Контракт выдачи ссылок потребуется описать перед реализацией: текущий `extract` их агенту не публикует.

### P3. Объединение выдач — после появления пригодных источников

RRF из R26 — простой кандидат без обучения. Сначала проверка обязательных ограничений и нормализация/дедупликация URL, затем объединение рангов с сохранением происхождения. Одинаковый upstream не считать независимым подтверждением. Не ранжировать выше мусор только потому, что он повторился у нескольких адаптеров. Польза на наших RU/EN случаях не измерена.

## Границы исследования и проверки

Приоритет источников: сопровождаемые исходники, документация авторов, статьи arXiv/ACL и PDF авторов. Для статей указана глубина чтения в отдельном каталоге; обзор не является систематическим метаанализом. Связанные issue сообщают наблюдения пользователей и не заменяют наш эксперимент. Две страницы OpenReview потребовали browser verification; использованы доступные arXiv, издательские и авторские страницы, без обхода проверки. Инструмент поиска HF не был доступен при вызове; это не мешало проверить первичные ссылки напрямую.

Добавлены только исследовательский ignored-тест, его fixture, оценка и документация. Основной search остаётся с прежними параметрами; новые сервисы, зависимости, ключи и изменения VPS/MCP-конфигурации не добавлены. После добавления пробы: **14 обычных тестов прошли, 8 ignored**, `cargo fmt --check` и `cargo clippy --all-targets -- -D warnings` прошли с locked/offline-зависимостями. Полный новый сетевой прогон, собственный индекс, браузерные сравнения и калибровка oMLX не выполнялись. Качество поиска остаётся незакрытым риском.
